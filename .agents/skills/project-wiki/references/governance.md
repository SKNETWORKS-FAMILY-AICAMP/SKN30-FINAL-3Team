# 위키 운영 규칙

## 목적

이 위키는 에이전트와 개발자가 개발에 필요한 프로젝트 지식을 낮은 탐색 비용으로 공유하기 위한 저장소 내 정본이다. 사람용 기획서나 WBS를 대체하지 않는다.

## 문서 구조

- `references/index.md`를 공통 지식의 시작점으로 사용한다. 기능별 계약과 검증 기록은 해당 기능·모듈의 라우터에서 필요한 문서로 연결한다.
- `references/` 바로 아래 또는 한 단계의 분류 폴더에 최종 문서를 둔다.
- 분류별 인덱스를 만들지 않는다. 문서 수가 많아져 루트 인덱스로 탐색하기 어려울 때만 추가한다.
- 빈 문서와 빈 분류를 미리 만들지 않는다.
- 한 파일에는 하나의 검색 의도와 책임만 둔다. 큰 계약은 공통 규칙과 독립적으로 변경하는 기능별 계약으로 분리한다. 파일 길이 자체보다 작업자가 함께 읽어야 하는 범위를 기준으로 삼는다.
- 스킬 본문은 프로젝트 고유 경계와 조건부 읽기에 집중한다. 일반 개발 설명, 반복된 완료 기준과 실행 이력을 누적하지 않는다.
- 현재 계약과 구현 상태는 소유 정본에서 관리하고 과거 실행·비교 근거는 기본 읽기 경로에서 분리한다. 인덱스에 같은 상태 설명을 복제하지 않는다.

## 결정 소유권

- project-wiki에는 프로젝트 공통 아키텍처, 모듈 경계, 공통 계약, 개인정보, 개발환경과 Git 정책을 기록한다.
- 한 모듈 내부의 구조, 라이브러리, 패턴, 테스트와 런타임 선택은 `.agents/skills/<module>/references/`에 기록한다.
- 모듈별 ADR은 해당 모듈의 `references/decisions/index.md`에서 관리한다.
- 모듈 결정이 다른 모듈의 공개 계약이나 프로젝트 경계를 바꾸면 project-wiki에 별도 프로젝트 ADR을 작성한다.
- 같은 결정을 두 위치에 복제하지 않고 정본에 링크한다.

## 지식 상태

| 상태 | 의미 | 사용 조건 |
|---|---|---|
| 출처 | 원문에서 검증됨 | 출처 식별자나 링크를 함께 기록 |
| 결정 | 팀이 승인함 | ADR 또는 승인된 정책에만 사용 |
| 구현됨 | 저장소나 환경에서 확인됨 | 확인 경로를 함께 기록 |
| 계획됨 | 구현 의도가 있음 | 완료된 것처럼 표현하지 않음 |
| 제안 | 선택지로 검토 중 | 장단점과 결정 필요 사항을 기록 |
| 미확정 | 정보가 없거나 충돌함 | `open-questions.md`에 연결 |

하나의 문서에 여러 상태가 섞이면 문장이나 표의 행에 상태를 표시한다.

## 원문 반영

사람이 새 기획, 요구사항 또는 기능 명세를 제공하면 다음 순서로 처리한다.

1. 개발에 영향을 주는 정보만 추출한다.
2. 기존 위키와 충돌하는지 확인한다.
3. 승인 여부에 따라 `결정`, `계획됨`, `제안`, `미확정`을 구분한다.
4. 적절한 정본 문서 한 곳에 반영한다.
5. 원문 위치와 반영 범위를 `sources/manifest.yaml`에 등록한다.
6. 중요한 충돌은 임의로 해결하지 말고 사용자에게 알린다.

## 제품 요구사항 관리

- 승인 상태와 무관하게 저장소에서 관리하는 제품 요구사항의 편집 정본은 `docs/requirements/`의 분할 문서다.
- `docs/requirements/index.md`를 요구사항 전용 라우터로 사용하며 project-wiki 루트 인덱스에서는 이 라우터에 직접 연결한다.
- 전달받은 원문은 `docs/requirements/sources/`에 변경하지 않는 출처 스냅샷으로 보존한다.
- 요구사항의 저장 위치가 승인 상태를 뜻하지 않는다. 승인 전 내용은 `출처`, `계획됨`, `제안` 또는 `미확정`으로 표시한다.
- project-wiki에는 요구사항 전체를 복제하지 않고 프로젝트 공통 아키텍처, 계약, 개인정보 정책과 결정만 짧게 반영한다.
- 요구사항 ID와 구현·테스트의 연결은 `docs/requirements/traceability.yaml`에서 관리하고 상세 요구사항 문장을 복제하지 않는다.

## 변경 책임

- 모든 팀원과 에이전트는 자신의 기능 브랜치에서 위키를 수정할 수 있다.
- 코드와 위키가 함께 변하면 같은 PR에서 검토한다.
- PR 설명에 바뀐 결정, 계약, 개인정보 영향이 있는지 명시한다.
- 일반 변경은 팀 검토를 거쳐 `dev`에 병합된 내용을 공유 지식으로 승인하고, `main`은 릴리스 기준으로 갱신한다.
- 브랜치와 PR 운영은 저장소 루트 `.agents-rule/git.md`를 유일한 정본으로 사용한다.

## 갱신 절차

1. 공통 지식은 이 위키에, 모듈 내부 지식은 해당 모듈 references의 정본 한 곳에 반영한다.
2. 새 문서는 가장 가까운 기능·모듈 인덱스에 읽는 조건과 함께 연결한다. 공통 진입점이 생기면 루트 인덱스도 갱신한다.
3. 미확정 사항은 소유 범위의 `open-questions.md`에 질문, 영향과 결정 주체를 기록한다. 별도 질문 파일이 없는 모듈은 해당 모듈 지침을 따른다.
4. 승인된 아키텍처·정책 결정은 소유 범위의 ADR과 결정 인덱스에 기록한다. 승인되지 않은 후보는 `제안` 또는 미해결 질문으로 남긴다.
5. 의미 있는 위키 변경은 `log.md`에 한 줄로 요약한다. 외부·사람용 원문을 반영하면 `sources/manifest.yaml`에 위치와 반영 범위를 등록하고 원문 전체를 복사하지 않는다.

## 삭제와 대체

- 승인된 ADR을 암묵적으로 덮어쓰지 않는다. 결정을 변경하면 기존 ADR을 보존하고 상태를 `대체됨`으로 바꾸며 새 ADR에 대체 번호와 이유를 명시한다.
- 더 이상 유효하지 않은 구현 설명은 Git 이력만으로 충분한 경우 삭제할 수 있다.
- 문서를 이동하면 해당 인덱스와 내부 링크를 같은 변경에서 수정한다. PR 리뷰 정책의 파일·절 선택도 함께 갱신해 필수 근거가 빠지지 않게 한다.
- `.claude/skills/`의 name·description은 공용 스킬과 동기화하고 본문은 import로만 공유한다.

## 품질 기준

- 제목과 표를 이용해 검색 가능한 용어를 사용한다.
- 날짜는 `YYYY-MM-DD`로 기록한다.
- 확실하지 않은 숫자, 비용, 버전은 확정값처럼 기록하지 않는다.
- 비밀값, 개인정보 원문, 접근 토큰은 절대 기록하지 않는다.
- 같은 지식을 여러 문서에 복제하지 않고 링크한다.

## 문서 검증

스킬·참조·리뷰 경로 변경 후 저장소 루트에서 `node .github/scripts/check-skill-docs.mjs`를 실행한다. 공용/Claude 메타데이터·import, 스킬 문서의 상대 파일 링크와 PR 리뷰 정책의 파일·절 존재를 검사한다. 링크의 절 앵커와 계약 의미 보존은 별도로 검토한다.

읽기량 비교에는 `node .github/scripts/check-skill-docs.mjs --measure <문서 경로...>`에 해당 작업에서 읽을 문서만 전달한다. 같은 작업의 변경 전후를 비교하고 필수 계약·개인정보·검증 지침이 빠지지 않았는지 함께 확인한다. 문자·줄 수는 파일량이며 실제 모델 입력 토큰이나 비용 측정값이 아니다.
