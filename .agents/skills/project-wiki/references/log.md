# 위키 변경 로그

- 2026-08-23: F3 실행 재사용, 결과 조회와 사용자 피드백 API 를 구현했다. `POST /api/v1/f3/runs` 는 `(사무소, 앵커 종류, 앵커 ID, input_data_version)` 의 재사용 가능한 실행(`QUEUED`·진행 중·`COMPLETED`)이 있으면 새로 만들지 않고 그것을 돌려주며(F3-CR-12), 실패 종료 실행은 재사용하지 않는다. 동시 접수는 PostgreSQL transaction advisory lock 으로 직렬화하고 프로세스 메모리 lock 을 쓰지 않는다. **AI 구성은 재사용 키에 없다.** 접수 시점에는 어떤 모델로 돌지 알 수 없으므로 구현 가능한 키와 그 한계를 계약에 그대로 적었다. `GET /api/v1/f3/runs/{run_id}/result` 는 앵커 카드와 근거, 후보 조회 조건, 전체·카드화·남은 후보 수, 후보별 등급·순위·비교 근거·걸림돌·양보 지점·행동 제안·기각 사유·근거를 돌려주며 전체 후보를 대상으로 페이징한다. 판정하지 않은 후보에는 등급을 붙이지 않고, 15건 이후 후보의 추가 카드화는 구현하지 않았음을 명시했다. 응답에서 사무소·요청자·모델 설정·프롬프트·실행 스냅샷·lease·내부 실패 원문을 제외한다. `POST /api/v1/f3/feedback` 은 기존 `ai_decision_feedback` 에 저장하고 `brokerage_id`·`created_by` 를 세션에서만 도출하며 CSRF 를 요구한다. 사유는 고정 어휘 4종이고 자유문 `detail` 은 500자 상한과 개인정보 패턴 검사를 지나며 위반 시 422 `PERSONAL_DATA_NOT_ALLOWED` 다. 다른 사무소 대상은 404 다.
- 2026-08-23: F3 Worker polling loop 와 실제 handler 를 연결했다. `WORKER_ENABLED=false` 는 그대로 대기하고, `true` 면 DB readiness 와 AI 설정을 먼저 확인한 뒤 `claim_next_run` 을 반복한다. Provider 와 모델 ID 를 코드에서 고르지 않고 사무소의 활성 `ai_model_config` 에서 가져오며, LLM Provider 설정이 하나도 없으면 실행을 집기 전에 `ConfigurationError` 로 기동을 거부한다. 큐가 비면 `stop_event.wait(timeout)` 으로 기다려 busy loop 를 만들지 않고, 프로세스 수명 동안 asyncio loop 하나를 유지해 `AsyncOpenAI` client 가 깨지지 않게 했다. Worker 는 어떤 단계를 부를지 정하지 않고 **저장된 상태**가 정본이며, 한 번 claim 한 실행은 같은 lease 아래에서 끝까지 간다. 선점 대상에 lease 가 만료된 모든 진행 상태를 포함해 파이프라인 중간에 죽은 실행이 방치되지 않게 하고, 회수해도 진행 상태를 되돌리지 않는다. `JUDGING` 에서 끊긴 실행은 저장된 결과가 없을 때만 되돌린다. 오류는 입력 변경 → `SUPERSEDED`, 계약·PII·바인딩·설정 → `FAILED_TERMINAL`, 일시 오류 → lease 반납 후 재시도, lease 상실 → 무기록 종료로 분류한다. 재시도는 새 scheduler 나 heartbeat 없이 기존 5분 lease 와 3회 상한을 그대로 쓰고 상태를 바꾸지 않으므로 `FAILED_RETRYABLE` 은 만들지 않는다. 공개 `failure_message` 는 고정 문구만 저장하고 운영 로그에도 예외 타입 이름까지만 남긴다.
- 2026-08-23: F3 중개 판정 저장과 완료 전이를 구현해 `JUDGING`·`COMPLETED` 를 실제 상태로 기록했다. 앵커 카드 1장과 후보 카드 N장을 한 번의 AI 호출로 판정하고(F3-NF-04), 준비·호출·저장 세 단계로 나눠 모델을 기다리는 동안 DB 잠금을 쥐지 않는다. 판정 입력 카드는 저장된 `analysis_snapshot` 을 그대로 되살려 만들고, 어떤 카드를 넣을지는 후보 카드 단계가 붙여 둔 `candidate_cards` 가 정한다. 저장 직전에 lease·사무소·바인딩·앵커 버전·후보 카드 집합·카드 활성 여부를 다시 확인하고, 결과 교차 검증과 개인정보 패턴 검사를 통과해야만 `match_evaluation`·`match_candidate_evaluation`·`match_candidate_evidence` 를 원자 저장하며 `COMPLETED` 로 옮긴다. 일부 후보만 저장된 채 완료되는 상태는 생기지 않는다. 기각도 사유와 함께 남긴다(F3-BR-10). 판정 단계에는 상담 원문이 없으므로 인용 offset 은 새로 계산하지 않고 카드가 저장해 둔 값을 그대로 옮기며, 카드에 없는 인용은 거절한다. 대리와 판정이 다른 모델을 쓸 수 있도록(F3-NF-10) `BROKERAGE_JUDGMENT` capability 설정을 따로 요구하고, 그 바인딩은 새 컬럼 없이 `redacted_output_snapshot` 에 allowlist 필드만 기록한다. 후보 0건은 모델 호출과 `JUDGING` 없이 빈 최종 결과를 원자 저장하고 완료한다. 새 migration 없이 기존 006 테이블만 사용했다.
- 2026-08-23: F3 중개 판정의 Backend–AI 공개 계약(`brokerage-judgment:v1`)과 생성 구현을 추가했다. 앵커 카드 1장과 후보 카드 N장을 한 번의 구조화 출력 호출로 판정하며 앵커를 후보 수만큼 반복 전송하지 않는다(F3-BR-01, F3-BR-02, F3-NF-04). 등급 어휘를 `STRONG`·`WEAK`·`REJECTED` 로 고정하고 화면 한국어 매핑을 계약 문서에 기록했으며, 행동 제안의 접촉 경로도 `CALL`·`MESSAGE`·`IN_PERSON` 하나의 enum 으로 고정했다(F1 의 `interaction_channel` 과 다른 축). 판정 입력 카드는 포지션 카드 계약의 `PositionCardAnalysis` 를 그대로 재사용한다. 검증은 후보 집합 정확 일치, 순위 1..N 연속, 기각 사유 필수, 근거 1건 이상, 앵커·측면 일치를 강제하고, 판정 단계에 상담 원문이 없으므로 인용은 그 카드가 이미 갖고 있던 `(interaction_id, quote_text)` 쌍만 허용한다. 승인된 개인정보 경계를 지키기 위해 `brokerage_id`·`run_id` 를 AI 계약에 넣지 않고 카드 ID 로 요청·결과를 대조한다. 중개 판정에는 LangGraph 를 쓰지 않는다. 구조화 출력 1회짜리 단일 노드 graph 는 이름뿐인 wrapper 이고, 현재 단계 경계와 재개는 Backend DB 상태가 담당하며 checkpoint 저장소는 여전히 미확정이다(AI ADR-0002).
- 2026-08-23: F3 후보 포지션 카드 확보 단계를 구현하고 `CANDIDATE_CARDS_READY` 를 실제 상태로 기록했다. 앵커 카드 생성 코드를 후보에도 쓸 수 있게 공용화해 snapshot 조립·마스킹·PII 검사·cache key·cache lookup·저장 직전 재검증을 한 벌만 유지했고, 대상(`CardTarget`)과 기대 실행 상태만 인자로 받는다. 후보 카드는 앵커의 반대편 `negotiation_side` 를 쓰고 입력 버전은 그 후보 장부 행의 `row_version` 이며, cache hit 이면 모델을 부르지 않는다. 후보 카드는 child `AgentRun` 을 만들지 않고 루트 실행에 직접 귀속해 lease 와 결과 소유권을 한 행에 유지한다. 후보는 순차 처리해 SQLModel `Session` 을 async task 사이에서 공유하지 않는다. 후보 하나라도 실패하면 상태를 옮기지 않고, 후보 0건은 모델 호출 없이 통과한다. 확보한 카드 ID 는 같은 snapshot 의 `candidate_cards` 에 붙여 중개 판정이 어떤 카드를 넣었는지 확정할 수 있게 했다.
- 2026-08-23: F3 결정적 SQL 후보 추출을 구현하고 `CANDIDATES_READY` 를 실제 상태로 기록했다. 후보 조회는 LLM 을 쓰지 않고 앵커 **카드**의 첫 번째 거래 유형 추정가를 축으로 반대편 장부를 조회하며(F3-SQ-03), 사무소·소프트 삭제·부모 세대 삭제·가격 밴드·희망 단지를 SQL 조건으로 걸고 가격 근접도·평형 일치·접수 최신성을 점수로만 반영한다(F3-SQ-04). 점수와 정렬은 Python `Decimal` 6자리로 계산하고 점수→접수일→ID 오름차순 tie-breaker 로 결정적 순서를 보장한다. 상위 15건만 카드화하되 전체 후보의 ID·구성 점수·순위·조회 조건을 `match_evaluation.candidate_selection_snapshot`(`candidate-selection:v1`)에 보존해 컷이 아니라 페이징이 되게 했다(F3-BR-13, F3-BR-14). 후보 0건도 조회 조건과 함께 정상 완료한다(F3-CR-11). `match_evaluation` 을 후보 단계의 헤더로 먼저 만들어 새 테이블을 추가하지 않았고, 가격 밴드 0.1·평형 오차 1평·가중치는 승인된 수치가 아닌 MVP 조정값으로 snapshot 에 함께 저장한다.
- 2026-08-21: 앵커 포지션 카드의 실행 중 변경 감지를 전면 보강했다. 앵커 `row_version` 만으로는 세대 스펙·단지명·당사자 역할·날짜 신호 변화를 볼 수 없어, AI에 보낸 요청 전체를 정규화한 SHA-256 입력 지문(`position-card-input:v1`)을 도입하고 cache key 를 `position-card:v3` 로 올려 지문과 로그 범위 지문을 함께 넣었다. snapshot의 `as_of`와 파생 날짜 신호를 UTC 기준으로 통일해 동일 순간의 시간대 표기가 달라도 실제 AI 요청과 지문이 같게 했다. 저장 단계는 범위를 현재 장부에서 다시 만들어 준비 이후 생긴 당사자 관계를 감지하고, cache hit 카드 행을 `FOR UPDATE`로 잠가 활성 확인과 `ANCHOR_READY` 전이 사이의 동시 무효화를 직렬화하며, 모델 바인딩 네 값(`model_snapshot` 포함)을 모두 대조한다. 미바인딩 판정을 `model_snapshot = '{}'::jsonb` 조건까지 포함하도록 고쳐 손상된 행을 덮지 않는다. 매물 대리 로그 범위에서 세대에만 달리고 당사자도 없는 모호한 로그를 제외했다.
- 2026-08-21: 앵커 포지션 카드 구현의 격리·개인정보 구멍을 막았다. 대리 측면별 상담 로그 범위를 `InteractionScope` 하나로 정의해 같은 세대에 달린 반대편 당사자의 로그가 매물 대리 입력에 섞이지 않게 했고, 요청자·담당자·로그 작성자와 실제로 선택된 로그 당사자의 식별값까지 마스킹 대상에 넣었으며 `handover_condition`도 같은 마스킹을 거치게 했다. 모델 출력 자유 문자열을 저장 직전에 훑어 금지 패턴이나 가렸던 식별값이 다시 나타나면 전체 저장을 거절한다. source identity 재검증을 cache hit 경로에도 적용하고, cache lookup이 대상·버전·상담 집합까지 대조하게 했다. 실행의 모델·prompt·workflow 바인딩을 lease fencing 아래 최초 1회 기록하고 재시도에서 고정하며, allowlist 필드만 model snapshot으로 저장한다. `target_label`은 Backend가 F1 구조화 값에서 만들어 모델이 바꿀 수 없게 했다. 준비 단계는 모든 예외에서 transaction을 닫는다.
- 2026-08-20: F3 앵커 포지션 카드의 생성·검증·저장 수직 슬라이스를 구현했다. AI는 `position-card-prompt:v1`·`position-card-workflow:v1`로 구조화 출력 1회를 내고 모델 출력 schema에서 대상·source·장부 표기 금액을 아예 제외했다. Backend는 F1 장부와 상담 로그 전량을 읽어 길이 보존 마스킹을 적용한 뒤 날짜 신호와 함께 요청을 조립하고, AI 호출 전후로 transaction을 분리해 모델을 기다리는 동안 DB를 쥐지 않으며, 저장 직전에 lease·앵커 버전·source identity를 다시 확인한다. 거래 유형별 금액을 잃지 않도록 migration 012로 `negotiation_position_price`를 추가했고 가격이 하나일 때만 기존 scalar 컬럼을 호환 projection으로 채운다. 근거는 마스킹 본문 기준 offset과 함께 저장하고 `ANCHOR_READY`를 실제 상태로 기록한다. Worker polling, 후보 추출, 중개 판정과 운영 Provider·모델은 여전히 미구현·미확정이다.
- 2026-08-20: F3 포지션 카드의 Backend–AI 계약을 `contracts/f3-ai.md`로 확정했다. `negotiation_side`를 `LISTING`·`REQUIREMENT`로 고정해 OQ-012를 종료하고, 계약 버전 `position-card:v1`을 cache key 버전 `position-card:v2`와 별개 축으로 분리했으며, intent·urgency·contactability·evidence·price_kind 어휘와 화면 한국어 매핑, LISTING/REQUIREMENT 입력 격리, 근거 필수 규칙, 마스킹된 상담 로그만 전달하는 개인정보 경계를 정의했다. F3-SE-03의 원문 보관 요구보다 승인된 개인정보 정책의 전체 프롬프트·응답 로그 금지를 우선한다. 프롬프트, 모델 호출, LangGraph workflow, 카드 저장과 `ANCHOR_READY` 전환은 아직 구현하지 않았고 운영 Provider·모델은 미확정이다.
- 2026-08-20: F3 매물 앵커가 F1 세대 소프트 삭제를 따르도록 매물 단건 조회 범위에 부모 세대 삭제 여부를 포함하고, `agent_run.requested_by`의 보존·삭제를 개인정보 정책 정본에서 `agent_run` 감사 이력과 같은 생명주기로 확정해 OQ-007 범위를 미확정 항목만으로 좁힘. 배포용 Worker 프로세스는 있으나 polling loop·handler는 없다는 구현 상태와 활성 실행 재사용·`SUPERSEDED`·SSE 미구현을 F3 아키텍처와 API 계약에 같은 사실로 반영함.
