# ADR-0035: F3 조건부 자동 판정과 저장 결과 조회

- 승인 범위: 2026-09-09 프로젝트 요청자의 1차 기획 구현 요청. 팀 병합 검토 전이며 공유 dev 배포 승인이 아니다.
- 출처: [구현 요청](../../../../../docs/requirements/sources/f3-expansion-implementation-2026-09-09.md)
- 부분 대체: [ADR-0018](ADR-0018-f3-save-trigger-anchor-card-scope.md)의 저장 시 카드까지만 자동 생성하고 완료 결과를 재사용하지 않는 정책.
- 유지: ADR-0006 모듈 경계, ADR-0014 합성 입력 경계, 최초 상위 5건 판정, 사무소 공유 결과·기존 피드백 의미.

## 배경

요청마다 완료 판정을 다시 실행하면 사용자가 대기하며 저장된 결과를 다시 발견하기 어렵다.
GPU 상시 운영 조건에서는 동일 가동시간의 임대료보다 준비된 결과 비율·대기·공유 모델 처리량이 중요하다.
요청자는 별도 워크트리에서 기획된 1차 방향을 필요한 모듈 전체에 구현하고 API·브라우저 통합 검증을 요청했다.

## 결정

1. 공통 ‘교차 판정’ 목록, 양쪽 장부 상세 요약, 후보 상세·양측 카드·기존 기록 확인을 제공한다. 조회는 모델 호출·작업 생성 없이 GET으로 수행한다.
2. 장부·상담·관계·단지 등 실제 입력의 변경은 PostgreSQL trigger가 같은 transaction에서 revision과 병합 outbox에 기록한다. outbox 기록 실패는 원장 저장도 rollback한다. 기존 F1 commit 뒤 접수 실패를 무시하던 경로를 대체한다.
3. 자동 기능은 `F3_AUTO_JUDGMENT_ENABLED`로 활성화한다. 기본 false는 점진 출시를 위한 운영값이며 활성화 시 유효 대상의 의미 있는 변경·날짜/모델 변화·누락을 Worker가 검증하고 필요한 전체 판정을 실행한다. 비입력 수정과 동일 결과는 재추론하지 않는다.
4. `POST /f3/runs`는 현재 입력·후보·모델 identity가 유효한 완료 실행 또는 진행 실행을 재사용한다. 필요한 경우만 새 작업을 만든다. 기존 202 응답 형태와 run 상태 조회는 유지한다. 카드 전용 legacy 작업은 사용자 요청으로 승격할 수 있다.
5. 완료 결과와 최신성은 분리한다. 원천 변경 즉시 이전 분석으로 표시하고, 새 결과는 최종 입력/lease 검증을 통과한 transaction에서 게시한다. 새 후보 유입도 검증한다. 공개 불가·미생성·무후보·미판정은 구별한다.
6. API와 Worker는 같은 EC2의 별도 프로세스/컨테이너 구성을 유지한다. 내구성·선점은 PostgreSQL에 두며 여러 Worker의 모델 실행은 DB 슬롯으로 제한한다. SQS·새 GPU·별도 Worker EC2를 필수 도입하지 않는다.
7. 후속 챗봇은 Backend 조회/접수 유스케이스를 재사용한다. 이번 변경에서 챗봇 F3 도구를 활성화하지 않고 대화 취소·삭제와 공유 Worker 작업 수명을 분리한다.

## 결과와 한계

기존 장부 저장의 성공 의미가 outbox 원자성까지 포함하도록 바뀐다. DB 변경과 Backend 배포는 함께 진행해야 한다.
사무소 단위 revision은 보수적으로 결과를 stale 처리한다. 소비자는 실제 입력 identity를 비교해 관계없는 변경의 모델 재실행을 피한다.
자동 flag가 꺼져 있어도 변경 이벤트는 보존되며 읽기·수동 접수는 제공한다. 저장 뒤 legacy 카드 접수를 별도로 수행하지 않는다.
상시 GPU의 임대료가 같아도 CPU·DB·모델 경합은 남는다. 현재 단일 API의 챗 실행 1건과 전역 F3 실행 1건/후보 최대 5개가 상한이며 다중 API 전환에는 챗 동시성 제한의 공유화가 필요하다.

구체적인 HTTP·상태·화면은 [확장 계약](../../../../../docs/architecture/f3/expansion-contracts.md), 검증·운영은 [구현 기록](../../../../../docs/architecture/f3/implementation-and-validation.md)에 둔다.

2026-09-09 후속 명명 요청에 따라 상태 테이블은 기존 `match_evaluation`과 같은 도메인의 `match_source_revision`, `match_change_outbox`, `match_target_state`로 명명한다. 적용 이력과 데이터는 [021 전진 migration](../../../../../docs/db/migrate/021_ALTER_MATCH_AUTOMATION_NAMES.sql)으로 보존한다.
