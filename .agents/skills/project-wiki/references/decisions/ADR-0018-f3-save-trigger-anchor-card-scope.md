# ADR-0018: F1 저장 트리거는 앵커 포지션 카드까지만 실행하고 판정은 사용자 요청이 이어받는다

- 상태: 승인됨
- 결정일: 2026-08-31
- 승인 주체: 프로젝트 요청자
- 대체 범위: [API 계약](../contracts/api.md)의 `F1 저장 후 자동 접수`가 규정하던 **저장 1건 = 판정 완주** 계약을 대체한다. 같은 절의 `Worker 선점과 lease`, 상태 수명주기와 실행 재사용 규칙도 이 결정의 범위에 포함한다.
- 관련 요구사항: [교차 판정](../../../../../docs/requirements/f3/cross-judgment.md) F3-CR-01~04
- 관련 계약: [API 계약](../contracts/api.md)
- 관련 아키텍처: [F3 온라인 런타임](../../../../../docs/architecture/f3/online-runtime.md)

## 맥락

종전 계약에서 F1 저장은 F3 실행 1건을 접수했고, Worker가 그 실행을 앵커 포지션 카드 →
후보 조회 → 후보 카드 → 중개 판정까지 끝까지 진행했다. 저장이 사용자가 명시적으로 일으킨
사건이고 그 순간의 맥락에서 답이 나와야 한다는 것이 근거였다.

운영에서 드러난 문제는 저장의 대부분이 **판정 결과를 보려는 저장이 아니라는 점**이다.
오타 수정, 담당자 메모 정리, 가격 한 자리 교정 같은 저장에서도 모델 판정이 완주했다.
후보 카드 생성과 중개 판정은 이 기능에서 가장 비싼 두 단계이고, 그 비용을 사용자가 선택한
적이 없다. F3-CR-03·04를 상세 진입 자동 실행에서 버튼 실행으로 바꾼 2026-08-27 개정과
같은 이유가 저장 경로에 그대로 남아 있었다.

반대로 앵커 포지션 카드는 사정이 다르다. 카드는 저장 시점의 장부 값으로 만들어야 정확하고,
입력 버전이 그대로면 나중에 재사용할 수 있다. 카드까지 미리 만들어 두면 사용자가 판정을
요청할 때 기다리는 시간이 줄고, 만들어 둔 카드는 판정을 요청하지 않아도 포지션 카드 조회에
쓰인다.

## 결정

저장 트리거가 자동으로 수행하는 범위를 **앵커 포지션 카드 생성까지**로 한정한다.

- `trigger_type=LEDGER_SAVE` 실행은 앵커 카드를 저장해 `ANCHOR_READY`가 되면 거기서 멈춘다.
  후보 조회, 후보 카드, 중개 판정은 자동으로 수행하지 않는다.
- 멈춘 실행은 Worker 선점 대상에서 제외한다. lease가 만료돼도 다시 집어가지 않는다.
- 멈춘 실행은 최대 시도 정리 대상에서도 제외한다. 주차는 실패가 아니라 사용자 요청을
  기다리는 상태이므로 `FAILED_TERMINAL`로 종료하지 않는다.
- 사용자가 상세에서 판정을 요청하면 같은 앵커·입력 버전의 활성 실행에 그 요청을 기록한다.
  `QUEUED`·`RUNNING`·`ANCHOR_READY` 어느 상태에서든 기록하며, 요청 시점에 따라 실행이
  갈라지지 않게 한다. 이때 `trigger_type`을 요청자의 값으로 옮기고 `requested_by`는 최초
  값을 유지한다.
- `ANCHOR_READY`에서 이어받을 때만 lease를 비운다. 진행 중인 Worker의 lease는 건드리지
  않는다.
- 주차 뒤의 첫 선점은 계획된 handoff이므로 `attempt_count`를 늘리지 않는다. 저장 단계가
  판정 단계의 실패 재시도 예산을 미리 쓰지 않게 한다.
- 새 실행을 만들지 않는다. 새로 만들면 앵커 카드 단계를 다시 지나 저장이 이미 치른 비용을
  한 번 더 쓴다.

## 대체하는 종전 계약

| 항목 | 종전 | 이 결정 |
|---|---|---|
| 저장이 수행하는 범위 | 앵커 카드 → 후보 조회 → 후보 카드 → 판정 → `COMPLETED` | 앵커 카드 → `ANCHOR_READY` 정지 |
| `ANCHOR_READY`의 의미 | Worker가 이어서 진행하는 중간 상태 | 중간 상태이자 사용자 요청을 기다리는 대기 지점 |
| Worker 선점 대상 | 구현된 진행 상태 전부 | `LEDGER_SAVE`+`ANCHOR_READY` 조합 제외 |
| 최대 시도 정리 | 만료·상한 초과 진행 상태 전부 | 같은 조합 제외 |
| 실행 재사용 시 `trigger_type` | 최초 값 불변 | 사용자 판정 요청이 들어오면 요청자 값으로 이동 (`requested_by`는 불변) |
| 선점 시 `attempt_count` | 항상 +1 | 계획된 handoff 선점은 유지 |

## 결과

판정 비용이 사용자가 결과를 보겠다고 요청한 경우로 한정된다. 앵커 카드는 저장 시점 맥락으로
남아 있어 요청 시 추가 카드 비용이 없다. 화면은 종전과 같은 실행 ID를 돌려받으므로 실행
식별자 계약은 바뀌지 않는다.

대신 사용자가 끝내 판정을 요청하지 않으면 실행이 `ANCHOR_READY`로 남는다. 이 실행은 Worker를
붙잡지 않고 실패로도 뒤집히지 않지만 종료 상태에 도달하지도 않는다. 보존 기간이 지난 실행
정리는 `retention_until`·`purged_at`을 쓰는 별도 작업의 범위로 남기며, 그 작업을 만들 때
주차 실행을 정리 대상에 포함할지 함께 정한다.

`trigger_type`이 옮겨지면 그 실행이 자동 접수에서 시작했다는 사실은 컬럼에 남지 않고
`f3_ledger_save_run_resumed` 로그로만 확인할 수 있다. 자동 접수 건수를 컬럼으로 집계해야 할
운영 요구가 생기면 별도 컬럼을 추가하는 후속 결정이 필요하다.

## 고려한 대안

- **종전 수명주기 유지**: 저장마다 판정을 완주시킨다. 구현이 단순하지만 이 결정의 동기인
  비용 문제가 그대로 남는다.
- **저장이 아무것도 하지 않음**: 트리거를 없앤다. 앵커 카드를 저장 시점 맥락으로 만들 기회를
  잃고, 사용자가 판정을 요청할 때마다 카드부터 만들어 대기 시간이 길어진다.
- **사용자 요청 시 새 실행 생성**: 주차 대신 저장 실행을 완료 처리하고 요청은 새 실행을
  만든다. 상태 기계가 단순해지지만 앵커 카드 단계를 다시 지나고, 저장 실행을 `COMPLETED`로
  적으면 후보가 0건인 완료 판정과 구분되지 않는다.
