# ADR-0025: 캘린더 일정 저장은 F4가 소유하고 Time Keeper 조회에 통합한다

- 상태: 승인됨
- 결정일: 2026-09-04
- 승인 주체: 프로젝트 요청자
- 대체 범위: [F4 제외 범위](../../../../../docs/requirements/f4/scope-and-open-questions.md)의 "일정
  데이터 저장·캘린더 동기화는 F1(F1-SC)이 소유하고 F4는 읽기만 한다"는 기존 정리를 대체한다.
- 관련 요구사항: [F4 캘린더](../../../../../docs/requirements/f4/calendar.md),
  [F4 Time Keeper](../../../../../docs/requirements/f4/time-keeper.md), F1 일정(F1-SC-01~05, 미구현)
- 관련 계약: [API 계약](../contracts/api.md)

## 맥락

F4는 이제까지 F1 장부의 날짜를 조회만 했다(Time Keeper, `F4-CM-06`). "사용자가 캘린더에 일정을
직접 추가해 관리한다"는 요청이 들어오면서 그 일정을 저장할 테이블이 처음으로 필요해졌다.

기존 문서(F4 제외 범위 6장)는 "일정 데이터 저장·캘린더 동기화는 F1이 소유한다(F1-SC)"고
정리해 두었다. F1-SC-01~05(일정 등록·조회·담당자 필터·유형 구분)는 아직 구현되지 않았고, 원래
매물장이 관리자·계약과 함께 다루는 범용 일정 기능을 가리키는 항목이었다. 이번 요청은 그보다
좁다 — F4의 "다가오는 일정" 브리핑과 짝을 이루는 캘린더이며, F2 음성 인식에서 감지된 일정
후보를 승인해 넣는 것까지 F4 안에서 끝내는 흐름을 전제로 한다(F2 연동은 후속 작업, 이 ADR의
범위 밖).

F1-SC를 먼저 구현해 F4가 그것을 조회만 하는 안도 검토했지만, F1-SC는 범위가 더 넓고(담당자별
색상 구분, 유형 구분 등 매물장 전반의 일정 관리) 이번 요청과 직접 관련이 없는 설계 결정을
먼저 요구한다. F4가 필요한 만큼만 소유하는 편이 더 작고 검증 가능한 단위다.

## 결정

1. **저장 소유권**: 사용자가 캘린더에서 직접 만드는 일정은 F4가 소유한다. `calendar_event`
   테이블(`018_CREATE_CALENDAR.sql`)은 `backend/src/domain/calendar/`가 관리하며, F1 장부
   테이블(`property_unit`/`property_listing`/`property_requirement`)과는 별개다. 세대·매물·
   손님을 가리키는 연결 컬럼은 두지 않는다 — 이번 요청 범위가 요구하지 않고, F1-SC가 나중에
   별도로 구현되어도 이 테이블과 충돌하지 않는다.
2. **조회 통합**: `GET /api/v1/time-keeper/agenda`(F4-TK, "다가오는 일정")는 `calendar_event`를
   여덟 번째 union 갈래로 포함한다. 사용자에게는 "다가오는 일정"과 "캘린더"가 하나로 이어진
   같은 목록의 두 형태로 보여야 하기 때문이다 — 저장은 나뉘어도 사용자가 보는 목록까지 나뉘지
   않는다. 이 갈래는 `AgendaCategory` 고정 열거형을 쓰지 않고 사용자가 고른 임의 문자열을 그대로
   싣는다.
3. `docs/requirements/f4/scope-and-open-questions.md`의 제외 범위 표를 이 결정에 맞게 고친다.
   F1-SC는 계약 건 관리 같은 매물장 전반의 일정 기능으로 범위를 좁혀 존치한다.

## 결과

- F4가 처음으로 쓰기 권한을 갖는 테이블이 생겼다. `F4-CM-06`(F4는 F1 장부를 직접 고치지
  않는다)은 위반하지 않는다 — `calendar_event`는 F1 장부 테이블이 아니다.
- Time Keeper는 여전히 조회 전용이다. 쓰기 가능한 테이블의 데이터를 읽어 오지만 이 API 자체는
  아무것도 쓰지 않는다.
- 나중에 F1-SC를 실제로 구현하면(세대·매물·손님과 연결된 일정) 그 데이터도 같은 union에
  아홉 번째 갈래로 추가할 수 있다. 이 ADR은 그 가능성을 막지 않는다.
- F2 연동(음성 인식 일정 후보 → 승인 팝업 → `calendar_event` 저장)은 이 테이블 위에서 이어갈
  수 있지만 코드는 이 결정의 범위에 없다.

## 고려한 대안

- **F1-SC를 먼저 구현**: 캘린더가 F1-SC를 조회만 한다. 기존 문서의 원래 계획과 맞지만, F1-SC의
  전체 범위(담당자 필터·색상, 유형 구분)를 먼저 설계해야 해서 이번 요청보다 훨씬 크다.
- **프론트엔드에서만 병합**: 저장뿐 아니라 "다가오는 일정" 응답도 그대로 두고 캘린더 화면이
  두 API를 따로 불러 화면에서 합친다. 창(`within_days`·`overdue_days`)·종류별 상한 같은 계산
  규칙을 프론트엔드에 다시 구현해야 해서 규칙이 두 곳에 흩어질 위험이 있다. 사용자가 "다가오는
  일정에도 함께 뜨게" 요청한 것과도 어긋난다 — 배지·아침 브리핑 등 기존 Time Keeper 진입점이
  캘린더 일정을 모르게 된다.
