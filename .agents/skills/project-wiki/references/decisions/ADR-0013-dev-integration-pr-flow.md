# ADR-0013: dev 통합 브랜치와 main 릴리스 PR 흐름

- 상태: 승인됨
- 결정일: 2026-08-24
- 대체 대상: [ADR-0003](ADR-0003-main-pr-flow.md)
- 세부 정책: [브랜치 및 PR 정책](../../../../../.agents-rule/git.md)

## 맥락

팀의 일반 개발 PR과 개발 전달 파이프라인은 실제로 `dev`를 기준으로 운영한다. 기존 main 직접 PR 결정과 실제 흐름이 달라 같은 작업의 PR을 닫고 대상 브랜치를 바꾸어 다시 여는 일이 반복됐고, 개발 통합 상태와 릴리스 기준도 구분할 필요가 생겼다.

## 결정

- `dev`를 개발 통합 브랜치, `main`을 실행·배포 가능한 릴리스 기준 브랜치로 사용한다.
- 기능, 수정, 문서, 리팩터링과 유지보수 작업 브랜치는 최신 `dev`에서 만들고 `dev`로 PR을 연다.
- `main`은 `dev → main` 릴리스 PR로 갱신한다. 긴급 수정은 `main` 대상 PR로 처리한 뒤 `dev`에 동기화한다.
- 작업 PR은 squash merge하고, `dev → main` 릴리스 PR은 조상 관계를 보존하기 위해 merge commit을 사용한다.
- 모든 병합 PR은 작성자 외 사람 1명의 승인을 받는다.
- AI 리뷰는 사람 승인과 결정적 검증을 대체하지 않는 권고 자료로 유지한다.
- 브랜치 보호는 `dev`와 `main` 모두 직접 push와 force push를 막고, 승인과 각 브랜치에 필요한 결정적 검증을 요구하도록 구성한다.

## 결과

일반 개발 변경은 `dev`에서 조기에 통합하고 `main`은 명시적인 릴리스 단위로 유지할 수 있다. 대신 `dev`가 장기간 검증 불가 상태가 되지 않도록 작업 PR을 작게 유지해야 하며, 릴리스 PR에서 포함 변경과 통합 검증·배포 위험을 다시 확인해야 한다. `dev → main`을 squash하면 다음 릴리스 비교에서 이미 배포한 커밋이 다시 나타날 수 있으므로 릴리스 PR에는 squash merge를 사용하지 않는다.
