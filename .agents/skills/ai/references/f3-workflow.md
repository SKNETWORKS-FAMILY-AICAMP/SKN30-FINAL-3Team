# F3 워크플로 내부 구조

`ai/src/brokerage_ai/f3/` 의 구성과, 이 패키지가 소유하지 **않는** 것을 적는다.

## 소유 범위

| 파일 | 소유하는 것 |
|---|---|
| `contracts.py` | 프레임워크 중립 DTO. Backend 와 주고받는 유일한 타입 |
| `prompts.py` | 프롬프트 원문의 정본과 `PROMPT_VERSION` |
| `routes.py` | 역할별 `ModelRoute` 와 temperature |
| `workflow.py` | 모델 호출 2종(`build_position_card` · `judge_matches`)과 입력 조립 |

`ai/` 가 소유하지 않는 것 — 후보 추출, 인도 가능일·마감일 계산, 보류 게이트, 등급 산출,
카드 캐시, 영속화. 전부 Backend `domain/negotiation/` 에 있다. 이 경계 덕분에 등급 규칙을
모델 없이 단위 테스트할 수 있다.

## 흐름 제어가 Backend 에 있는 이유

[찾기] 는 후보 추출(SQL) → 카드 캐시 조회 → 캐시 미스분만 모델 호출 → 판정 → 등급 순인데,
가운데 두 단계가 DB 조회다. 흐름을 `ai/` 에 두면 Agent 가 DB 를 알아야 한다. 그래서 Backend 가
단계를 진행하고 `ai/` 는 각 모델 호출만 맡는다.

## LangGraph 보류

ADR-0002 가 F3 에 LangGraph 를 채택했으나 이 슬라이스는 쓰지 않는다. 흐름 제어가 Backend 에
있어 그래프가 붙을 자리가 없고, 같은 ADR 도 이번 기반 작업에서 production graph 를 만들지
않는다고 적어 두었다. 재개(중단 후 이어하기)가 실제로 필요해질 때 다시 판단한다. 그 시점의
후보는 — 판정 1회를 그래프 노드로 쪼개는 것이 아니라, 캠페인(B군) 같은 장시간 실행을
그래프로 올리는 쪽이다.

## 프롬프트 버전

`PROMPT_VERSION` 은 카드 캐시 키의 재료이자 `agent_run.prompt_version` 에 기록된다.
프롬프트를 고치면 반드시 올린다 — 올리지 않으면 옛 프롬프트로 만든 카드가 캐시 히트로
살아남아 판정 결과를 오염시킨다.

프롬프트 본문은 줄바꿈까지 `06_프로토타입_F3플로우/agents.py` 와 같게 유지한다. 프로토타입과
등급이 갈릴 때 원인이 프롬프트인지 나머지 구현인지 갈라보기 위해서다. 이 대조가 끝나면
자유롭게 고쳐도 된다.

## 대리 격리

매물 대리와 손님 대리가 서로의 로그를 읽지 않는 것은 프롬프트 문구가 아니라 **입력 타입**으로
보장한다. `PositionCardInput` 에 반대편을 담을 필드가 없다. 프롬프트의 「손님 정보는 받지
않았고 알 필요도 없다」 는 두 번째 방벽이지 첫 번째가 아니다.
