# 평가 설계 지침

## 평가 계약

평가를 구현하기 전에 다음을 버전된 계약으로 정의한다.

- 평가 질문과 의사결정 목적
- 비교할 기준선과 변경 후보
- 평가 단위와 사례 포함·제외 조건
- 성공, 부분 성공, 실패와 판정 불가 규칙
- 자동 지표와 사람 평가의 역할
- slice, 집계 방식, 결측·오류 처리
- 합격 임계값의 상태와 결정 주체
- 데이터셋, 평가 코드, 모델·프롬프트와 실행 환경 버전

요구사항의 수용 기준과 금지 동작을 우선 사용한다. 승인되지 않은 목표 수치를 합격선으로 만들지 않는다.

## 지표 선택

지표는 작업 형태와 실패 비용에 맞게 선택하고 산식과 정규화 규칙을 함께 고정한다.

| 작업 형태 | 검토할 지표 |
|---|---|
| 분류 | 정확도, macro/micro F1, 클래스별 정밀도·재현율, 혼동 행렬 |
| 정보 추출 | 필드별 정밀도·재현율·F1, exact/normalized match, 누락·환각률 |
| 음성 인식 | CER/WER, 중요 개체와 숫자 단위 정확도 |
| 검색·후보 추출 | Recall@K, Precision@K, MRR, 필터 위반률 |
| 순위·판정 | pairwise 정확도, 순위 상관, 기각·보류 오류율 |
| 생성·근거 | 근거 지지율, 요구사항 충족률, 금지 내용 생성률, 사람 평가 |

전체 평균만 보고하지 말고 실패 비용이 큰 클래스와 slice를 별도로 보고한다. 여러 지표를 단일 점수로 합치면 가중치와 근거를 명시한다.

## Slice와 도전 사례

- 입력 길이, 품질, 난이도와 결측 정도
- 주요 클래스와 희소 클래스
- 정상, 경계, 충돌, 거부·보류 사례
- 합성, 실제, 증강 등 원천 유형
- 개인정보 마스킹과 정규화가 결과에 미치는 경우
- 운영 환경에서 중요한 도메인 조건

slice 정의는 데이터 계약에 포함하고 결과를 본 뒤 유리하게 재정의하지 않는다. 새 오류 유형을 발견하면 기존 최종 평가를 덮어쓰지 말고 다음 데이터셋 버전에 도전 사례를 추가한다.

## 사람 평가

- 자동 지표로 판단하기 어려운 항목만 사람 평가로 보완한다.
- 평가 항목, 점수 척도, 판정 예시와 판정 불가 조건을 작성한다.
- 모델 이름과 비교군을 가능한 범위에서 가린다.
- 동일 사례를 복수 평가자가 판단하게 하고 일치도와 불일치 해소 절차를 기록한다.
- 평가자의 전문성, 이해관계와 개인정보 접근 범위를 제한한다.
- 자유 의견과 정량 점수를 분리해 보관한다.

## 무결성과 재현성

- 최종 평가 데이터와 정답을 튜닝·프롬프트 작성·검색 인덱스에서 차단한다.
- 개발 중 반복 확인한 데이터는 최종 평가로 승격하지 않는다.
- 실패 사례를 기준선에는 누락하고 후보에만 포함하는 비대칭 비교를 금지한다.
- 같은 데이터셋과 평가 계약으로 기준선과 후보를 다시 실행할 수 있게 한다.
- 무작위성이 있으면 반복 횟수, 시드, 변동 범위와 집계 방식을 기록한다.
- 실행 실패, 타임아웃, 파싱 실패를 결과에서 제외하지 말고 별도 오류로 집계한다.

## 모듈 연동

Data는 데이터셋 버전, 정답, slice와 평가 계약을 제공한다. AI는 모델 실행, 지표 구현, 실험 추적과 결과 산출을 소유한다. Backend는 승인된 운영 피드백을 계약으로 제공할 수 있지만 Data와 AI가 운영 DB에 직접 의존하게 하지 않는다.

평가 계약이 여러 모듈의 완료 판정이나 공개 인터페이스가 되면 project-wiki에 정본을 두고 이 문서에는 일반 절차만 유지한다.
