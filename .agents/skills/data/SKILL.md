# 데이터셋과 평가 데이터 개발

이 스킬은 특정 기능의 필드, 지표 또는 합격 기준을 정본으로 보관하지 않는다. 작업할 때마다 프로젝트 요구사항에서 현재 평가 대상을 확인하고, 재현 가능한 데이터셋과 평가 계약으로 변환한다.

## 시작 절차

1. 저장소 루트 AGENTS.md와 project-wiki의 references/index.md를 읽는다.
2. 기능 범위, 입력·출력, 금지 동작과 수용 기준은 요구사항 인덱스에서 관련 정본만 찾아 읽는다.
3. references/index.md에서 현재 작업에 필요한 데이터 설계 또는 평가 설계 지침만 읽는다.
4. 개인정보나 외부 데이터가 있으면 project-wiki 개인정보 정책과 출처 등록 상태를 확인한다.
5. 모듈 경계나 공개 데이터 계약을 변경하기 전에 프로젝트 결정 인덱스와 관련 ADR을 확인한다.
6. 저장 포맷, 저장 위치, 분할 정책, 라벨링 절차, 평가 기준이 미확정이면 승인된 결정처럼 구현하지 말고 소유 범위의 open-questions.md에 기록한다.

## 책임과 경계

data/는 다음을 소유한다.

- 원천 등록, 수집, 비식별화, 정제, 변환과 적재 파이프라인
- 정답 라벨과 평가 입력의 생성·검수·계보
- 데이터셋 분할, 버전, manifest, 체크섬과 재현성
- 스키마, 필수값, 중복, 분포, 오염과 누수에 대한 데이터 품질 검증
- 운영 데이터의 입력 품질 검사와 품질 보고서

data/는 다음을 소유하지 않는다.

- 모델 호출, 프롬프트, Agent, 그래프, 추론 어댑터와 실험 실행
- HTTP API, 인증·인가, 업무 규칙, 운영 DB 트랜잭션과 Repository
- 사용자 화면과 IaC
- 테스트 코드

실행환경과 의존성은 data/ 안에서 독립 관리하고 루트 공통 Python 환경이나 공통 패키지를 미리 만들지 않는다. 실제 규모와 반복이 확인되기 전에는 내부 폴더와 추상 계층을 고정하지 않는다.

모델 성능 평가를 구현하거나 실행할 때는 ai 스킬을 함께 사용한다. Data는 평가 데이터, 정답, slice와 평가 계약을 제공하고, AI는 모델 실행, 지표 계산, 실험 추적과 결과 생성을 담당한다. 운영 시스템의 승인 전후 데이터나 사용자 피드백을 평가 데이터로 가져오려면 Backend가 제공하는 승인된 계약을 사용하며 운영 DB에 직접 결합하지 않는다.

## 데이터셋 작업 절차

1. 요구사항에서 평가할 동작, 관측 가능한 입력·출력, 금지 동작과 실패 조건을 추출한다.
2. 평가 단위와 사례 식별 규칙을 정하고 원천, 이용 조건, 개인정보 등급과 보존 조건을 등록한다.
3. 원본, 중간 산출물, 정제 데이터와 배포 데이터의 계보를 유지한다.
4. 라벨 정의, 불명확·판정 불가 처리, 정규화와 검수 절차를 명시한다.
5. 동일 주체·원천·시나리오의 누수를 막는 그룹 기준으로 데이터셋을 분할한다.
6. 스키마, 중복, 누락, 분포, 근거 참조, 개인정보와 분할 누수를 검증한다.
7. 검증을 통과한 불변 산출물에 버전, manifest와 체크섬을 부여한다.
8. 소비 모듈에는 내부 파이프라인이 아니라 버전된 데이터 계약과 산출물 위치만 노출한다.

상세 설계는 [dataset-design.md](references/dataset-design.md)를 따른다.

## 평가 설계 절차

1. 평가 질문, 비교 기준선, 평가 단위와 실패 비용을 먼저 정의한다.
2. 요구사항의 성공·금지·보류 동작을 각각 측정 가능한 판정 규칙으로 바꾼다.
3. 전체 점수만 두지 말고 중요한 오류 유형과 데이터 slice별 결과를 분리한다.
4. 자동 지표로 판단할 수 없는 품질은 사람 평가 기준, 평가자 수, 불일치 해소 절차를 정의한다.
5. 개발 중 사용하는 데이터와 최종 판정 데이터를 분리하고 최종 평가 정답을 모델 입력과 튜닝 과정에서 차단한다.
6. 지표 산식, 집계 방식, 결측 처리, 임계값 상태와 실행 환경을 버전으로 고정한다.
7. 모델 또는 파이프라인 변경 전후를 같은 데이터셋 버전과 평가 계약으로 비교한다.

구체적인 지표 선택과 사람 평가 절차는 [evaluation-design.md](references/evaluation-design.md)를 따른다. 요구사항에 없는 합격 임계값을 임의로 승인된 기준처럼 만들지 않는다.

## 개인정보와 평가 무결성

- 개발·평가에 실사용자 개인정보를 기본 사용하지 않는다.
- 원문 개인정보, 비밀값과 인증정보를 저장소·로그·프롬프트에 기록하지 않는다.
- 외부 처리자에게 전달되는 필드, 저장 여부, 리전과 삭제 조건을 확인한다.
- 평가 정답, 숨김 slice와 최종 평가 사례가 추론 입력이나 튜닝 데이터에 섞이지 않게 한다.
- 합성 데이터는 합성임을 표시하고 실제 분포를 대표한다는 근거 없이 성능을 일반화하지 않는다.
- 라벨 수정과 평가셋 변경은 기존 버전을 덮어쓰지 말고 새 버전으로 발행한다.

## 검증과 완료 조건

- 파이프라인의 입력과 출력 스키마, 필수값, 중복, 건수와 참조 무결성을 검사한다.
- 데이터 계보, 설정, 난수 시드, 코드 버전과 체크섬으로 산출물을 재현할 수 있게 한다.
- 분할 누수, 정답 오염, 개인정보 잔존과 주요 slice 누락을 검사한다.
- 데이터 품질 검증은 운영 파이프라인 기능으로 구현하고 data/에 테스트 코드를 추가하지 않는다.
- 평가 계약 변경 시 AI 평가 소비자와의 호환성을 확인한다.
- 승인·구현된 품질 명령만 실행하고 도구가 미확정이면 검증 공백을 보고한다.

## 지식 갱신

- 데이터 모듈 내부 구조, 도구, 저장 포맷, 분할·라벨링·품질 규칙은 이 스킬의 references와 결정 인덱스에 기록한다.
- 여러 모듈이 공유하는 데이터 계약, 평가 정책, 개인정보 정책과 합격 기준은 project-wiki에 기록한다.
- 기능별 입력·출력과 수용 기준은 요구사항 정본이 소유하며 이 스킬에 복사하지 않는다.
- 일회성 실행 결과, 임시 오류 분석과 검증되지 않은 추측은 정본에 기록하지 않는다.
