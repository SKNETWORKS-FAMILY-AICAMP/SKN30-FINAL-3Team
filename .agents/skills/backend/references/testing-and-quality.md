# 백엔드 테스트와 품질 권장안

## 적용 원칙

- 테스트 비용을 변경 위험과 실패 비용에 비례시킨다. 모든 변경에 모든 테스트 계층을 요구하지 않는다.
- 계약, 개인정보, 동시성, 재처리와 마이그레이션처럼 실패 비용이 큰 경계는 강하게 검증한다.
- 단순 wiring이나 위험이 낮은 변경에는 가장 값싼 계층의 테스트와 승인된 정적 검사를 우선한다.

## 개발 흐름

- 도메인 규칙과 application 유스케이스는 가능하면 실패하는 Given/When/Then 테스트에서 시작하고 red-green-refactor로 진행한다.
- TDD를 기계적으로 강제하지 않는다. 설정, wiring 또는 탐색적 변경에서도 완료 전에 변경된 동작과 실패 경로를 자동화 테스트로 남긴다.
- 버그는 먼저 가장 작은 재현 테스트로 고정하고 원인을 수정한다. 구현 세부가 아니라 외부에서 관찰되는 회귀를 검증한다.
- 테스트 이름에 조건, 행동과 기대 결과를 드러낸다.

## 테스트 계층

| 종류 | 대상 | 기본 대역과 검증 |
|---|---|---|
| 도메인 단위 | 값 객체, 엔티티, 상태 전이, 순수 계산 | I/O 없이 불변식과 경계값 검증 |
| Application | command/query handler, 권한, Unit of Work 조율 | fake port와 fake clock/ID로 결과·호출·rollback 검증 |
| 통합 | DB adapter, query projection, outbox, migration | 운영과 같은 DB 엔진 및 실제 transaction으로 제약·SQL·호환성 검증 |
| 계약 | HTTP 요청·응답, 오류, 이벤트 schema | 공개 예제와 schema로 생산자·소비자 호환성 검증 |
| 얇은 종단간 | 핵심 진입점부터 실제 adapter 조합 | 소수의 중요 흐름과 wiring 검증 |

- 테스트가 책임을 중복하지 않게 가장 낮은 비용의 계층에서 동작을 검증하고, 모든 기능에 전체 피라미드를 만들지 않는다.
- 외부 HTTP, AWS SDK, 시계, UUID, 파일 시스템처럼 비결정적이거나 프로세스 밖인 경계만 대역으로 교체한다.
- 내부 도메인 객체와 private 메서드를 과도하게 mock하지 않는다. 상태와 반환값, 저장된 결과, 발행 계약처럼 관찰 가능한 결과를 검증한다.
- DB adapter와 migration을 SQLite 같은 대체 엔진만으로 검증하지 않는다. 운영 DB가 확정되면 같은 엔진을 통합 테스트에 사용한다.

## 위험 기반 시나리오

변경이 해당 위험을 만들 때 아래 시나리오를 검증한다.

- 같은 이벤트나 작업의 중복 전달과 재전달
- 처리 중 부분 실패, rollback과 안전한 재시도
- outbox 미발행 레코드 재처리와 중복 발행에 대한 소비자 멱등성
- 두 요청의 동시 수정 충돌과 lost update 방지
- 역할별 허용·거부, 필드 마스킹과 리소스 존재 유출 방지
- 로그, 오류, 이벤트와 DLQ에 비밀값·개인정보 원문이 남지 않음
- 시간대, 날짜 경계, 빈 입력, 최대 크기와 페이지 경계
- 대량 조회·검색의 정렬 안정성, 페이지 누락·중복과 목표 성능

해당 기능이 이벤트, 개인정보, 동시 수정 또는 대량 조회를 사용하지 않으면 관련 없는 시나리오를 억지로 추가하지 않는다.

## 호환성과 마이그레이션

- 레거시 문자열, 파일 또는 프로토콜 파서는 현재 동작을 characterization test로 고정한 뒤 변경한다.
- parse-render-parse 또는 encode-decode round-trip으로 손실과 모호성을 검증한다.
- API·이벤트의 호환되지 않는 변경에는 구버전 소비자 시나리오와 전환 계획을 테스트한다.
- DB 변경은 빈 DB와 기존 스키마 양쪽에서 전진 마이그레이션을 실행하고 데이터 보존, 제약, 인덱스를 확인한다.
- 파괴적 변경은 별도 승인된 복구 또는 단계적 전환 절차 없이 적용하지 않는다.

## 품질 게이트

- 임의의 전역 커버리지 숫자를 품질 목표로 두지 않는다. 변경된 동작, 핵심 분기, 실패 경로와 회귀 위험이 테스트되는지를 검토한다.
- 새 테스트가 수정 전 실패하고 수정 후 통과하는지 확인할 수 있으면 기록한다.
- flaky test를 재실행으로 숨기지 말고 비결정성의 원인을 제거한다.
- 포맷, 린트, 타입 검사, 단위·통합·계약 테스트 명령은 승인된 backend 도구와 설정이 생긴 뒤 `backend/` 내부 정본으로 고정한다.
- CI의 PostgreSQL 통합 검사는 `TEST_DB_URL`을 필수로 요구한다. DB fixture는 빈 migration DB에서 필요한 참조 행을 직접 만들고 기존 공유 데이터나 실행 순서에 의존하지 않는다.
- 사용할 명령이 아직 승인되거나 구현되지 않았으면 임의 도구를 프로젝트 표준으로 추가하지 말고 검증 공백을 결과에 명시한다.
- PR에는 변경한 계약, 마이그레이션, 개인정보 영향, 이벤트 재처리 방식과 실행한 검증을 요약한다.

## 현재 회귀 검사의 구성

- 인증 세션 정책은 고정 시각과 Repository I/O 대역으로 폐기·만료 경계, 계정 활성 상태, 마지막 활동 갱신 간격과 절대 만료 상한을 검증한다.
- F2 HTTP 입력 경계는 유효한 요청과 거절 요청을 함께 검증한다. 잘못된 JSON·필드 타입, UTF-8 바이트 상한, 빈 음성·음성 크기 상한, 인증·CSRF 거절에서 provider 미호출과 임시 파일·접수 슬롯 정리를 확인한다.
- `tests/api/test_f2_ledger_f3_flow.py`는 가짜 F2 pipeline과 실제 HTTP·PostgreSQL을 조합해 분석만으로 업무 행을 저장하지 않고, 승인 후 F1 저장으로 접수된 F3 실행을 명시적 판정 요청이 재사용하는 흐름을 검증한다. 브라우저 필드 변환, 실제 모델 품질, Worker 판정 완료를 검증하는 테스트는 아니다.
- 실제 commit을 검증하는 F3 앵커 카드·중개 판정 테스트는 준비 코드를 각 `*_fixtures.py`로 분리한다. 두 파일의 `f3_committed_db.py`는 테스트가 만든 사무소 범위의 행만 정리한다. 외부 rollback transaction으로 바꾸면 다른 연결의 가시성·동시성·lease 검증 의미가 달라지므로 실제 commit 경계를 유지한다.
- 위키와 코드의 동기화 검사는 설명 문장이나 과거 로그 문구 대신 상태·버전 식별자와 구조화된 표의 구현 상태를 비교한다. 실제 개인정보·재사용·저장 정책은 동작 검사에서 검증한다.
