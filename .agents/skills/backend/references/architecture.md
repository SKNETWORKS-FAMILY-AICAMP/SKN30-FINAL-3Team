# 백엔드 아키텍처 권장안

## 적용 원칙

- 이 문서는 가능한 설계 선택을 안내하며 모든 기능에 동일한 계층과 패턴을 요구하지 않는다.
- 현재 요구를 충족하는 가장 단순한 구조에서 시작하고 복잡성, 변동성 또는 실패 위험이 확인될 때 구조를 추가한다.
- 승인된 [ADR-0001](decisions/ADR-0001-contextual-architecture-defaults.md)의 과설계 방지 기준을 먼저 적용한다.
- 프로젝트 공통 결정·계약·개인정보 정책과 승인된 백엔드 ADR이 이 문서보다 우선한다.

| 상황 | 우선 선택 |
|---|---|
| 단순 CRUD·관리 기능 | 얇은 입력 처리, 명시적인 함수·모듈, 필요한 DB 검증 |
| 불변식·상태 전이·계산 규칙 | 선택적 도메인 모델과 application 조율 |
| 대량·특화 조회 | 읽기 전용 query와 projection 검토 |
| 외부 시스템·변동성 높은 인프라 | port·adapter 검토 |
| 장시간·독립 재시도·모듈 간 연동 | 비동기 작업 또는 통합 이벤트 검토 |

한 기능에 모든 항목을 동시에 적용하지 않는다.

## 설계 단위와 의존성

- 기능 응집도와 변경 이유를 기준으로 경계를 찾고 실제 도메인 이름을 공통 스킬에 미리 고정하지 않는다.
- 새 기능은 하나의 모듈러 모놀리스 안에서 기능 단위로 응집시킨다. 루트 모듈 또는 배포 서비스를 추가하는 것으로 시작하지 않는다.
- 복잡성이 이를 정당화할 때 `domain`, `application`, `adapters`, `bootstrap` 역할을 구분한다. 단순 기능에 빈 계층이나 전달만 하는 클래스를 만들지 않는다.
- 소스 의존성은 `bootstrap -> adapters -> application -> domain` 방향으로만 흐르게 한다. 안쪽 계층이 바깥쪽 계층을 import하지 않게 한다.
- `domain`을 순수 Python으로 유지하고 HTTP, ORM, AWS SDK, 환경 변수, 프레임워크 lifecycle에 의존시키지 않는다.
- `application`이 유스케이스, 권한 확인, 트랜잭션 경계와 port 호출을 조율하게 한다. 도메인 불변식을 application에 복제하지 않는다.
- `adapters`가 HTTP·CLI·배치·메시지 입력과 DB·외부 API·큐 출력을 변환하게 한다.
- `bootstrap`에서 설정을 읽고 구현체를 조립한다. 설정 접근을 도메인 또는 application 코드에 흩뜨리지 않는다.

## 선택적 DDD

- 불변식, 상태 전이, 생명주기 또는 단위가 있는 값에는 엔티티, 값 객체, 애그리게이트를 검토한다.
- 둘 이상의 엔티티에 걸친 순수 비즈니스 계산이 특정 엔티티에 자연스럽게 속하지 않을 때만 도메인 서비스를 사용한다.
- 단순 CRUD, 관리 화면용 마스터 데이터와 읽기 projection에 전술적 DDD 패턴을 의무화하지 않는다.
- 애그리게이트는 일관성 경계로만 사용하고 조회 편의 때문에 크게 만들지 않는다. 다른 애그리게이트는 식별자로 참조한다.
- repository port는 애그리게이트 저장·복구 의미로 제한한다. 임의 SQL 질의를 모두 repository 메서드로 포장하지 않는다.

## Command, Query와 트랜잭션

- 상태를 바꾸는 command는 application 유스케이스를 통해 도메인 규칙과 Unit of Work를 실행하게 한다.
- 대량 그리드, 검색, 집계는 읽기 전용 query port와 projection을 사용할 수 있다. 조회를 위해 애그리게이트를 재구성하지 않는다.
- query 경로에서 상태를 변경하거나 command 불변식을 우회하지 않는다.
- 하나의 유스케이스를 기본 트랜잭션 경계로 삼는다. 외부 네트워크 호출을 열린 DB 트랜잭션 안에 두지 않는다.
- 동시 수정 가능성이 있으면 version 또는 동등한 낙관적 잠금을 사용하고 충돌을 명시적 application 오류로 반환한다. 마지막 저장이 이전 변경을 조용히 덮어쓰게 하지 않는다.
- 공개 DTO, application command/query, 도메인 객체, ORM·테이블 모델 사이의 변환 위치를 어댑터 또는 명시적 매퍼로 한정한다.

## Port와 오류 변환

- 저장소, Unit of Work, 외부 서비스, 메시지 발행, 파일 저장, 시계와 식별자 생성 중 대체 가능성·변동성·테스트 경계가 있는 항목에 `typing.Protocol` 기반 outbound port를 검토한다.
- port는 특정 프레임워크나 SDK 타입 대신 application에 필요한 최소 입력·출력을 표현한다.
- 인바운드 어댑터는 인증 컨텍스트와 입력 DTO를 command/query로 변환하고 application 결과를 전송 계약으로 변환한다.
- HTTP 상태 코드, ORM 예외, AWS SDK 예외와 큐 수신 객체를 adapter 경계에서 application/domain 오류와 공개 계약으로 변환한다.

## 이벤트와 비동기 작업

- 같은 기능 경계 안의 협업은 동기 application 호출을 기본으로 한다.
- 장시간 작업, 독립 재시도, 장애 격리 또는 루트 모듈 간 연동이 필요할 때 통합 이벤트나 비동기 작업을 사용한다.
- 도메인 이벤트는 한 경계 안에서 발생한 비즈니스 사실을 표현하고 인프라 타입을 포함하지 않는다.
- 통합 이벤트는 다른 프로세스가 소비하는 버전된 공개 계약으로 변환한다. project-wiki의 이벤트 봉투와 추적 식별자 규칙을 따른다.
- SQS 같은 큐 제품은 어댑터로만 취급한다. 도메인·application 코드에 SDK 메시지 타입, URL 또는 재시도 설정을 노출하지 않는다.
- DB 변경과 외부 메시지 발행이 함께 보장되어야 하면 같은 DB 트랜잭션에 outbox 레코드를 저장하고 별도 발행기가 전달하게 한다.
- 소비자는 메시지 또는 이벤트 식별자로 멱등성을 보장하고 중복·재전달을 정상 상황으로 처리한다.
- 재시도 가능한 일시 오류와 재시도해도 성공하지 않는 영구 오류를 구분한다. 최대 재시도와 DLQ는 개인정보 보존 정책 및 운영 관측성과 함께 설계한다.
- 이벤트 sourcing, 모든 상태 변경의 외부 발행, 전면 비동기 choreography와 조기 마이크로서비스 분리를 기본값으로 사용하지 않는다.

## 분리 판단

다음 증거 중 하나가 생길 때만 API, batch, event 또는 worker의 별도 배포를 제안한다.

- 독립적인 확장 또는 자원 프로필이 필요하다.
- 장애와 재시작 주기를 격리해야 한다.
- 런타임이나 의존성이 양립하기 어렵다.
- 소유 팀과 변경 주기가 안정적으로 분리된다.

분리 전에는 계약, 관측성, 배포와 운영 비용을 함께 제시하고 project-wiki의 승인을 받는다.
