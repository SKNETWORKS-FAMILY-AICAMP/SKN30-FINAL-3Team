# ADR-0001: 복잡도에 비례한 백엔드 아키텍처 기본안

- 상태: 승인됨
- 결정일: 2026-08-12

## 맥락

백엔드는 API, 배치와 이벤트 처리를 수용해야 하지만 초기 구현과 팀 규모는 작다. DDD, 포트·어댑터, Unit of Work, CQRS와 이벤트 패턴을 모든 기능에 일률적으로 적용하면 단순한 변경에도 파일·모델·인터페이스와 테스트가 과도하게 늘어날 수 있다. 반대로 경계와 비즈니스 규칙이 복잡해진 뒤 구조를 도입하면 결합과 중복이 커질 수 있다.

## 결정

다음 항목을 절대 규칙이 아닌 상황별 기본 권장안으로 사용한다.

- 하나의 모듈러 모놀리스에서 시작하고, 독립 확장·장애 격리·상이한 런타임 요구가 확인될 때만 배포 단위를 분리한다.
- 단순 CRUD와 조회에는 직접적이고 읽기 쉬운 흐름을 허용한다. 불변식, 상태 전이, 계산 규칙과 명확한 일관성 경계가 있을 때만 전술적 DDD를 적용한다.
- 외부 시스템, 변동성이 큰 인프라, 대체 구현 또는 유의미한 테스트 경계가 있을 때 port·adapter를 사용한다. 단일하고 안정적인 내부 구현을 인터페이스로 감싸는 것을 기본값으로 삼지 않는다.
- 대량·특화 조회가 도메인 객체 재구성 비용을 만들 때만 query projection을 사용한다.
- 같은 기능 경계 안에서는 동기 호출을 우선한다. 장시간 작업, 독립 재시도, 장애 격리 또는 모듈 간 계약이 필요할 때만 이벤트나 큐를 사용한다.
- DB 변경과 외부 이벤트 발행의 원자성이 실제로 필요할 때 outbox를 사용하고, 중복 전달 가능성이 있을 때 소비자 멱등성을 설계한다.
- TDD는 권장 흐름으로 사용하고 테스트 범위는 변경 위험에 비례시킨다. 계약, 개인정보, 동시성, 마이그레이션과 재처리처럼 실패 비용이 큰 경계는 자동 검증한다.
- 권장안에서 벗어나는 구현은 PR에 이유와 검증 방법을 남긴다. 반복되거나 장기 유지되는 변경은 새 백엔드 ADR로 기록한다.

## 과설계 방지 기준

다음 질문에 명확히 답할 수 없으면 패턴이나 계층을 추가하지 않는다.

- 어떤 현재 복잡성, 결합 또는 실패 위험을 줄이는가?
- 지금 존재하는 두 번째 구현이나 변동성 높은 경계가 있는가?
- 추가 모델·매퍼·인터페이스의 유지비보다 이점이 큰가?
- 더 단순한 함수, 모듈 또는 트랜잭션으로 같은 요구를 충족할 수 없는가?
- 제거 시 계약, 테스트 가능성 또는 안전성이 실제로 나빠지는가?

추측성 확장성, 이름만 다른 중복 모델, 모든 클래스의 repository·service·interface 생성, 사용하지 않는 도메인 이벤트와 미래 마이크로서비스를 위한 선분리는 근거로 인정하지 않는다.

## 결과

- 기능 복잡도에 맞춰 단순 구현과 구조화된 설계를 함께 사용할 수 있다.
- 동일한 모듈 안에서도 기능별 구조가 달라질 수 있으므로 PR에서 선택 이유를 확인해야 한다.
- 아키텍처 일관성보다 낮은 변경 비용을 택하는 경우가 생길 수 있다.
- 안전·개인정보·공개 계약과 프로젝트 경계는 이 유연성의 대상이 아니며 project-wiki의 승인된 정책을 따른다.

## 미결정

이 ADR은 웹 프레임워크, Python 버전·패키지 관리자, DB·ORM·마이그레이션 도구, 품질 도구, 큐 제품 또는 실제 폴더 구조를 확정하지 않는다.
