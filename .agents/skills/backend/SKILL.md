# 백엔드 개발

## 적용 수준

- 이 스킬의 아키텍처와 개발 방식은 절대 규칙이 아니라 반복 작업의 일관성을 위한 기본 권장안으로 사용한다.
- 문제 규모와 위험에 비해 구조·추상화·테스트 비용이 커지면 더 단순한 구현을 선택한다.
- 권장안에서 벗어날 때는 이유와 검증 방법을 PR에 남긴다. 반복 적용할 선택이면 [모듈 결정](references/decisions/index.md)에 ADR로 기록한다.
- 저장소 루트 지침, project-wiki의 프로젝트 결정·계약·개인정보 정책과 승인된 모듈 ADR은 권장안보다 우선한다.

## 시작 절차

1. 저장소 루트의 `AGENTS.md`와 project-wiki의 `references/index.md`를 읽는다.
2. [백엔드 참조 인덱스](references/index.md)에서 현재 작업과 관련된 권장안, 모듈 결정과 미해결 사항만 읽는다.
3. 작업에 해당하는 프로젝트 API·이벤트 계약, 개발환경, 개인정보 정책과 결정을 확인한다.
4. 변경을 `도메인 규칙`, `유스케이스`, `조회`, `인바운드 어댑터`, `아웃바운드 어댑터`, `마이그레이션` 중 필요한 책임으로만 분류한다.
5. 승인되지 않은 기술이나 구조에 의존하면 구현 전에 결정 상태를 확인하고 적절한 모듈 또는 프로젝트 ADR을 제안한다.

## 책임과 경계

- `backend/`에서 동기 API, 일반 배치, 큐 생산·소비, 이벤트 처리와 서버 오케스트레이션을 담당한다.
- LangGraph 그래프 내부는 `agent/`, 데이터 수집·정제 파이프라인은 `data/`, IaC는 `infra/`에 둔다.
- 다른 루트 모듈의 내부 구현을 직접 import하지 말고 승인된 API, 이벤트 또는 데이터 계약으로 연동한다.
- API, batch, event를 미리 별도 배포 단위로 나누지 않는다. 독립 확장, 장애 격리 또는 상이한 의존성이 확인될 때 분리를 검토한다.
- 백엔드 실행환경과 의존성은 `backend/` 안에서 독립 관리한다. 루트 공통 Python 환경이나 `packages/`를 만들지 않는다.

## 기본 권장안

- 모듈러 모놀리스에서 시작하고, 불변식·상태 전이·계산 규칙이 있는 핵심에만 선택적 DDD를 적용한다.
- API, 배치, 이벤트 소비자가 같은 동작을 수행하면 application 유스케이스 재사용을 우선 검토한다.
- 외부 시스템이나 변동성이 큰 경계에는 port·adapter를 검토하되, 단일하고 안정적인 구현까지 무조건 Protocol로 감싸지 않는다.
- 공개 API·이벤트 모델과 영속 모델을 분리하되, 단순 변환을 위한 중복 모델이 실익 없이 늘어나지 않게 한다.
- 같은 경계 안에서는 동기 호출을 우선하고, 장시간 작업·독립 재시도·모듈 간 연동이 필요할 때 이벤트나 큐를 검토한다.
- PostgreSQL, SQLModel, Alembic, SQS와 AWS SDK는 승인 전까지 후보로만 취급한다. AWS SDK를 IaC에 사용하지 않는다.

## 완료 조건

- 변경 위험에 비례해 자동화 테스트를 추가한다. TDD는 권장하지만 모든 변경에 동일한 절차를 강제하지 않는다.
- 버그 수정은 가능하면 실패 재현 테스트를 먼저 추가하고 수정 후 통과를 확인한다.
- API 또는 이벤트 계약을 변경하면 계약 테스트와 project-wiki 정본을 함께 갱신한다.
- DB 스키마를 변경하면 기존 데이터 호환성과 전진 마이그레이션을 검증하고, 파괴적 변경에는 복구 또는 단계적 전환 방안을 제시한다.
- 개인정보가 DB, 로그, 이벤트, 큐, 오류 또는 외부 서비스에 노출되는 경로를 점검한다.
- 승인·구현된 포맷, 린트, 타입 검사와 테스트 명령만 실행한다. 명령이 없으면 임의 표준을 확정하지 말고 검증 공백을 보고한다.
- 장기 유지할 모듈 내부 선택은 백엔드 references에, 프로젝트 공통 결정·계약·정책은 project-wiki에 갱신한다.
