# ADR-005: 데이터 출처를 기능 단위로 고른다

## 맥락

장부는 `VITE_LEDGER_SOURCE`로 mock과 실제 API를 바꿔 왔다. 백엔드가 없어도 화면을 완성할 수
있게 하려는 설정이고, 하나의 값이 애플리케이션 전체를 덮는 전제였다.

F3 교차 판정에서 그 전제가 깨졌다. Backend는 살아 있고 F1 장부 API도 정상인데
`WORKER_ENABLED=false`이면 F3 실행이 `QUEUED`에 머문다. 판정 완료 화면, 후보 등급, 기각 접기,
페이지네이션을 아무도 볼 수 없다. 실행 접수와 상태 조회는 실제 서버로 확인해야 하므로 장부까지
mock으로 내릴 수도 없다.

즉 **기능마다 가용성이 실제로 갈린다.** 한 값으로 전체를 덮으면 필요한 조합을 만들 수 없다.

## 결정

- 데이터 출처는 기능 단위로 고른다. 현재 값은 `VITE_LEDGER_SOURCE`와 `VITE_F3_SOURCE`다.
- **기능별 값은 선택이며 지정하지 않으면 장부 출처를 따른다.** 백엔드가 없는 환경에서 한
  기능만 실서버를 부르는 사고를 기본값으로 막는다.
- 값은 `mock` 또는 `api`뿐이고 그 밖의 값은 조용히 기본값으로 떨어지지 않고 거절한다.
- 팀 공통 기본값은 `frontend/.env.local`이 소유하고, 개인이 다르게 쓸 때는 `frontend/.env`에서
  덮는다. 기능별 값은 `.env.local`에 주석으로 안내만 두고 켜지 않는다.
- 각 기능은 transport 인터페이스를 두고 화면과 훅은 어느 구현인지 모른다. 선택은 기능의
  transport 선택자 한 곳에서만 한다.
- mock이 지어낸 응답은 **실제 decoder를 통과시킨다.** mock이 계약에서 어긋나면 화면이 아니라
  decoder가 먼저 잡아야 하고, mock으로 확인한 화면이 실서버로 바꿔도 같은 가정 위에서 돌아야
  한다.
- mock은 아직 계약에 없는 필드를 지어내지 않는다. 없는 필드를 채우면 화면이 만들어지지 않을
  기능을 준비하게 된다.

## 결과

- 장부는 `api`, F3만 `mock`으로 두고 판정 완료 화면을 확인할 수 있다.
- 설정 값이 하나 늘었다. 기능이 늘어날 때마다 값을 계속 추가하는 방식이 적절한지는 세 번째
  기능이 생길 때 다시 본다. 그때는 기능 목록을 받는 한 값이 나을 수 있다.
- mock은 실제 서버 동작의 증명이 아니다. 단계 전환과 화면 상태를 확인할 뿐이며, 종단 검증은
  검토된 합성 환경에서 따로 해야 한다.
