# 프론트엔드 개발 가이드

작업 규모와 위험에 맞는 가장 단순한 설계를 선택한다. 저장소 지침, 승인된 프로젝트 정책과 프론트엔드 ADR을 이 가이드보다 우선한다. 설치 버전과 실제 구현 상태는 `frontend/package.json`, lockfile과 코드에서 확인하고 문서의 표현만으로 추정하지 않는다.

## 작업 경계와 정본

- `frontend/`에서 화면, 사용자 상호작용, 브라우저 상태와 API 표현 계층을 담당한다.
- 서버 비즈니스 규칙, 에이전트 실행, 데이터 파이프라인과 IaC를 프론트엔드에 복제하지 않는다.
- 작업 전 project-wiki의 `references/index.md`와 `.agents/skills/frontend/references/index.md`에서 관련 문서만 읽는다.
- 화면 구조, Screen ID, 상태, 소유권 또는 화면 이동을 변경하기 전 `docs/screen/index.md`와 관련 화면 문서를 읽는다.
- HTTP 계약을 변경하거나 해석할 때 project-wiki의 `contracts/api.md`를 확인한다.
- 개인정보가 화면, 브라우저 저장소, URL, 분석 도구 또는 로그를 통과할 수 있으면 project-wiki의 개인정보 정책을 확인한다.
- UI를 변경할 때 `references/design/index.md`와 연결된 관련 세부 가이드를 따른다.
- 라이브러리, 구조 또는 개발 방식을 바꾸기 전 `references/decisions/index.md`와 관련 ADR을 확인한다.

## 작업 절차

1. 사용자 흐름, 수용 기준, API 계약과 권한 경계를 먼저 확인한다.
2. 성공뿐 아니라 loading, empty, no-match, error, offline, permission-denied와 재시도 상태를 정의한다.
3. 상태 소유자와 데이터 흐름을 정하고 가장 작은 변경 단위로 구현한다.
4. 기존 디자인 시스템과 공통 경계를 재사용하되, 아직 반복되지 않은 코드를 성급하게 공통화하지 않는다.
5. 타입 검사, 관련 테스트, 빌드, 접근성과 성능을 변경 위험에 비례해 검증한다.
6. 영구적인 모듈 결정은 frontend references에, 모듈 간 계약·정책 변경은 project-wiki에 기록한다.

## 아키텍처와 의존성

- 폴더보다 사용자 기능과 책임을 먼저 경계로 삼는다. 기능 모듈에는 해당 UI, 상태 조정, API 변환과 테스트를 가깝게 둔다.
- 애플리케이션 진입점과 라우트는 조합에 집중시키고 상세 비즈니스 규칙을 넣지 않는다.
- 모듈의 공개 진입점을 명시하고 다른 기능의 내부 파일을 깊은 경로로 가져오지 않는다.
- 의존 방향을 화면에서 기능 로직과 외부 경계 쪽으로 명확히 유지하고 순환 의존성을 만들지 않는다.
- React에 의존하지 않는 계산, 정책과 변환은 순수 함수로 분리한다.
- 여러 기능에서 실제로 반복되고 의미가 안정된 코드만 공통 영역으로 올린다. 이름만 포괄적인 `utils`, `common` 또는 거대한 공통 컴포넌트를 만들지 않는다.
- 브라우저 전용 API, 네트워크, 시간과 저장소 같은 부수 효과를 경계에 모으고 테스트에서 대체할 수 있게 한다.
- 새로운 계층, 전역 상태 또는 추상화는 해결할 구체적인 결합 문제와 제거할 중복을 설명할 수 있을 때만 도입한다.

## TypeScript

- TypeScript와 `strict` 검사를 프론트엔드 기본값으로 사용한다. 새 운영 코드는 원칙적으로 `.ts` 또는 `.tsx`로 작성한다.
- 기존 JavaScript를 변경할 때는 안전하게 검증 가능한 범위에서 함께 전환하고, 광범위한 마이그레이션은 별도 변경으로 분리한다.
- 컴포넌트 props, 공개 함수, API DTO, 저장소 데이터와 오류 경계에 명시적인 타입을 둔다. 함수 내부의 자명한 타입은 추론을 활용한다.
- `any`, 무검증 타입 단언과 non-null assertion으로 불확실성을 숨기지 않는다. 외부 입력은 `unknown`에서 시작해 좁힌다.
- API 응답, URL 파라미터, 브라우저 저장소와 사용자 입력은 타입 검사만 믿지 말고 런타임에서 검증한다.
- 로딩과 성공 여부를 서로 독립된 boolean으로 늘리지 말고 판별 가능한 상태 모델로 불가능한 조합을 제거한다.
- 도메인 개념에는 원시 타입보다 의미 있는 타입과 명확한 단위를 사용하되, 단순한 값까지 불필요하게 감싸지 않는다.
- `tsconfig`와 타입 관련 의존성을 바꾸면 엄격성 저하, 빌드 출력, 편집기 성능과 점진적 마이그레이션 영향을 함께 검증한다.

## React 컴포넌트와 상태

- 렌더링을 순수하게 유지한다. Effect는 외부 시스템과 동기화할 때만 사용하고, 사용자 이벤트 처리나 파생 값 계산을 Effect로 옮기지 않는다.
- 상태를 실제 소유자 가까이에 두고 필요한 범위까지만 끌어올린다. props 전달 자체를 피하려고 전역 상태를 추가하지 않는다.
- props나 다른 상태에서 계산할 수 있는 값은 중복 저장하지 않는다. 계산 비용이 실제로 문제가 될 때만 메모이제이션한다.
- 로컬 UI 상태, URL 상태, 서버 상태와 영속 브라우저 상태를 구분한다. 공유·새로고침·뒤로 가기가 의미 있는 값은 URL 표현을 우선 검토한다.
- 서버에서 받은 데이터를 불필요하게 복제하지 않고 캐시의 소유권, 갱신 조건과 오래된 데이터 처리 방식을 명시한다.
- 비동기 요청은 취소, 중복 제출, 순서 역전, 부분 실패와 재시도 동작을 정의한다.
- 큰 컴포넌트는 줄 수가 아니라 책임과 변경 이유를 기준으로 나눈다. 상속보다 조합과 명시적인 데이터 흐름을 우선한다.
- Suspense, transition, 서버 렌더링 또는 Server Components는 사용자 경험과 배포 제약을 검토하고 현재 런타임이 공식적으로 지원할 때만 채택한다.

## API와 외부 경계

- 네트워크 호출을 화면 곳곳에 흩뜨리지 말고 기능별 API 경계에서 요청, 응답, 오류와 취소를 다룬다.
- 전송 DTO를 화면 모델로 그대로 확산하지 않는다. 이름, 단위, null 가능성과 날짜 표현을 경계에서 변환한다.
- HTTP 성공 여부와 JSON 파싱 가능 여부를 구분해 처리하고, 예상 가능한 도메인 오류와 예기치 않은 오류를 다른 사용자 피드백으로 표현한다.
- 낙관적 업데이트는 실패 시 복구 방법과 중복 요청의 결과가 정의된 경우에만 사용한다.
- 비밀값을 번들, 클라이언트 로그, URL 또는 브라우저 저장소에 넣지 않는다.
- API 계약 변경이 필요하면 프론트엔드 내부에서 우회 구현하지 말고 계약 정본과 서버 소유자에게 변경을 연결한다.

## UI, 접근성과 콘텐츠

- 시맨틱 HTML과 네이티브 동작을 우선하고 ARIA로 잘못된 구조를 덮지 않는다.
- 키보드만으로 핵심 흐름을 완료할 수 있게 하고 포커스 순서, 포커스 표시, 모달 진입·복귀와 오류 이동을 검증한다.
- 상태와 의미를 색상, 아이콘 또는 위치 하나에만 의존해 전달하지 않는다.
- 폼에는 영구적인 레이블, 입력 목적, 오류 원인과 복구 방법을 제공한다.
- 비동기 변경과 중요한 상태를 보조 기술에 적절히 알리되 과도한 live region 알림을 만들지 않는다.
- 좁은 화면, 확대, 긴 번역 문자열과 사용자 글꼴 설정에서도 정보와 작업 순서를 보존한다.
- WCAG 2.2를 접근성 기준으로 삼고 복합 위젯은 설치된 디자인 시스템의 공식 키보드 패턴을 우선한다.
- 디자인 시스템 규칙에서 벗어나면 사용자 이점, 접근성·반응형·성능 영향과 검증 결과를 PR에 기록한다.

## 성능과 복원력

- 추측으로 최적화하지 말고 사용자 흐름, 프로파일과 실제 지표로 병목을 확인한다.
- 초기 JavaScript, 네트워크 요청, 이미지와 서드파티 코드의 비용을 기능 가치와 함께 검토한다.
- 화면·기능 단위 지연 로딩은 로딩 전환이 안정적이고 오류 복구 경계가 있을 때 적용한다.
- 긴 목록과 복잡한 그리드는 페이지네이션, 가상화와 서버 측 연산의 비용을 데이터 규모에 맞게 선택한다.
- 불필요한 렌더링을 숨기기 전에 상태 위치, props 안정성, 계산 범위와 컴포넌트 경계를 바로잡는다.
- 느린 네트워크, 중단된 요청과 부분 응답에서도 사용자가 현재 상태와 다음 행동을 이해할 수 있게 한다.

## 테스트와 품질 게이트

- 테스트를 구현 상세가 아니라 사용자가 관찰하는 동작과 공개 경계에 작성한다.
- 순수 변환과 상태 전이는 빠른 단위 테스트로, 컴포넌트 상호작용은 통합 테스트로, 핵심 사용자 흐름은 소수의 E2E 테스트로 검증한다.
- 성공 경로뿐 아니라 권한 거부, 빈 결과, 유효성 오류, 네트워크 실패와 재시도를 포함한다.
- 접근성 자동 검사를 사용하되 키보드, 포커스와 보조 기술 동작은 사람의 검토로 보완한다.
- 스냅샷이나 구현 세부 mock이 변경을 방해하면 더 좁은 동작 단언으로 바꾼다.
- 저장소에 정의된 명령을 먼저 확인하고 변경 범위에 맞는 타입 검사, 테스트와 프로덕션 빌드를 실행한다. 실행하지 못한 검증과 이유를 명시한다.

## 의존성과 결정 관리

- 새 의존성을 추가하기 전에 플랫폼, React, TypeScript와 기존 라이브러리로 해결 가능한지 확인한다.
- 유지보수 상태, 번들 비용, 접근성, 라이선스, 보안, 트리 셰이킹과 교체 비용을 검토한다.
- 버전별 API와 기능은 기억에 의존하지 말고 설치 버전에 맞는 공식 문서를 확인한다.
- 상태 관리, 라우팅, 데이터 패칭, 폼, 테스트 또는 빌드 도구를 새 표준으로 정하면 frontend ADR로 남긴다.
- 권장안에서 벗어나면 예외 이유, 영향 범위, 검증 방법과 공통화 여부를 PR에 기록한다.

## 완료 기준

- 요구사항과 화면 문서의 관련 상태를 구현한다.
- 타입 오류를 새로 만들지 않고 외부 입력을 런타임에서 검증한다.
- 로딩, 빈 결과, 오류, 권한과 재시도 상태를 확인한다.
- 키보드, 포커스, 반응형과 주요 접근성 동작을 확인한다.
- 관련 테스트, 타입 검사와 프로덕션 빌드 결과를 기록한다.
- 개인정보, 보안, 성능, 라이선스와 API 계약 영향을 검토한다.
- 새로 확정된 장기 지식을 올바른 정본에 반영한다.
