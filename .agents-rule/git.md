# 브랜치 및 Pull Request 정책

이 파일은 저장소의 브랜치와 PR 운영 정책에 대한 유일한 정본이다.

## 기본 브랜치

- `develop` 브랜치를 두지 않는다.
- 모든 변경은 짧게 유지하는 작업 브랜치에서 `main`으로 PR을 연다.
- `main`은 실행 가능하고 필수 검증을 통과한 상태로 유지한다.
- `main`에 직접 푸시하거나 강제 푸시하지 않는다.

## 작업 브랜치

작업을 시작할 때 최신 `main`을 기준으로 브랜치를 만든다.

브랜치 이름은 `<종류>/<영역>-<짧은-설명>` 형식을 사용한다.

| 종류 | 용도 | 예시 |
|---|---|---|
| `feat` | 새 기능 | `feat/agent-checkpoint` |
| `fix` | 버그 수정 | `fix/backend-timeout` |
| `docs` | 문서와 위키 | `docs/wiki-governance` |
| `refactor` | 동작을 바꾸지 않는 구조 개선 | `refactor/data-loader` |
| `chore` | 도구, 설정, CI, 인프라 유지보수 | `chore/infra-ci` |

에이전트 도구가 별도 접두사를 요구하면 해당 접두사 뒤에 위 형식을 유지한다.

## 변경 범위

- 하나의 브랜치와 PR은 하나의 검토 가능한 목적만 가진다.
- 관련 없는 수정은 포함하지 않는다.
- 요구사항, 계약, 아키텍처, 개인정보 처리 또는 운영 정책이 바뀌면 같은 PR에서 project-wiki를 갱신한다.
- 코드와 위키가 불일치하는 상태로 병합하지 않는다.
- 큰 작업은 독립적으로 검증하고 병합할 수 있는 작은 PR로 나눈다.

## PR 생성

- 작업 중 공유나 조기 검토가 필요하면 Draft PR을 사용한다.
- 구현과 필수 검증이 끝나면 Ready for review로 전환한다.
- PR 제목은 변경 목적을 한 문장으로 표현한다.
- 관련 Issue가 있으면 연결한다.

PR 설명에는 다음을 포함한다.

- 변경 목적과 범위
- 영향받는 모듈
- 주요 구현 또는 결정
- 검증 명령과 결과
- project-wiki 또는 ADR 변경 여부
- 개인정보, 보안, 인프라 비용 영향
- 남은 위험과 후속 작업

## 검토와 병합

- 최소 1명의 다른 팀원이 승인한다.
- 필수 자동 검사와 충돌 해결을 완료한다.
- 리뷰 의견이 남아 있다면 해결하거나 합의 내용을 기록한다.
- 기본 병합 방식은 squash merge를 사용한다.
- 병합 후 작업 브랜치를 삭제한다.
- PR 작성자가 단독으로 예외를 승인하지 않는다.
- `PR Policy Agent`의 AI 리뷰와 Discord 알림은 권고형이며 사람 승인을 대체하거나 병합을 승인하지 않는다.
- AI Check는 Required Check로 지정하지 않는다. 비밀 탐지, lint, type check, test, build처럼 안정화된 결정적 검사만 Required Check 후보로 삼는다.
- Discord 메시지는 알림 기록이며 승인·병합의 정본이 아니다.

## 긴급 수정

긴급 수정도 `fix/...` 브랜치와 PR을 사용한다. 빠른 병합이 필요하면 검토 범위를 최소화할 수 있지만 `main` 직접 수정, 검증 생략과 강제 푸시는 허용하지 않는다.

## 에이전트 작업

- 사용자가 변경 구현을 요청하면 현재 브랜치에서 파일을 수정할 수 있다.
- 브랜치 생성, stage, commit, push, PR 생성과 병합은 사용자의 요청 또는 승인 범위에서 수행한다.
- 기존 사용자 변경을 덮어쓰거나 관련 없는 변경을 commit하지 않는다.
- PR을 준비할 때 이 파일과 관련 모듈 스킬 및 project-wiki를 확인한다.
