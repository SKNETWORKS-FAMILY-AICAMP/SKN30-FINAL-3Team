## 제0부 공통 정의

### 0.1 이 문서를 읽는 법

세 기능은 따로 만들어졌지만 하나의 시스템이다. 본 통합본은 각 정의서의 내용을 **원문 그대로 보존**하고, 앞에 공통 장을 두어 세 기능의 경계와 연결 지점을 한자리에서 볼 수 있게 한다.

| 원칙 | 내용 |
|---|---|
| ID 체계 유지 | `F1-GR-01` `F2-POP-01` `F3-CR-05` 형식의 요구사항 ID를 원본 그대로 쓴다. 통합 과정에서 재부여하지 않는다 |
| 장 번호 유지 | 각 부의 장 번호는 원본을 따른다. 인용 시 「제1부 9.3장」처럼 부를 함께 쓴다 |
| 상충 시 우선순위 | 같은 대상을 두 부가 다르게 규정하면 **소유 기능의 정의가 우선**한다. 예 — 로그 append 규칙은 F1, STT 처리 절차는 F2, 판정 규칙은 F3 |
| 개정 | 원본 문서를 고치고 본 통합본을 다시 생성한다. 통합본만 고치지 않는다 |

### 0.2 시스템 개요

```text
                    ┌─────────────────────────────────┐
                    │        F1  장부 시스템           │
                    │  매물장(세대 전수 대장) · 구입장   │
                    │  상담 로그 · 일정 · 문자 · 권한   │
                    │        데이터의 단일 원천         │
                    └───────┬─────────────────┬───────┘
                     화면 접점              데이터 접점
                            │                 │
            ┌───────────────▼──┐        ┌─────▼──────────────────┐
            │   F2  STT 입력    │        │  F3  비서 에이전트      │
            │  음성메모 → 필드   │        │  매물 대리 · 손님 대리  │
            │  + 상담 로그 초안  │        │  중개 판정              │
            │  RunPod Whisper   │        │  교차 판정 · 배치 판정   │
            │  + 로컬 LLM       │        │                        │
            └──────────────────┘        └────────────────────────┘
```

F1이 데이터의 단일 원천이다. F2는 **입력 비용**을 낮추고, F3는 **누적된 데이터에서 판단**을 꺼낸다. F1이 현업 수준의 완결성을 갖지 못하면 나머지 두 기능은 시연 이상의 의미를 갖지 못한다.

### 0.3 기능별 책임 경계

| 구분 | F1 장부 시스템 | F2 STT 입력 | F3 비서 에이전트 |
|---|---|---|---|
| 한 문장 정의 | 장부를 저장하고 조회한다 | 말한 것을 장부 필드로 바꾼다 | 장부를 읽고 판단해 제안한다 |
| 입력 | 사람의 타이핑 · F2 결과 · F3 결과 | 음성메모 파일 | F1의 구조화 데이터 + 상담 로그 |
| 출력 | 화면 · 데이터 · 문자 발송 | 필드 제안값 + 상담 로그 초안 | 포지션 카드 · 등급/순위/행동 · 문안 초안 |
| AI 사용 | 없음 | RunPod Whisper + 로컬 LLM | 대리 2 + 중개 판정 |
| 데이터 쓰기 | 전권 | 사용자 승인 후 해당 행의 필드·로그 | **상담 로그 추가 · 일정 등록만** (F1-AG-03) |
| 실행 시점 | 상시 | 사용자가 [분석 실행]을 누를 때 | 저장·조회·캠페인 실행 시. 정기 배치 없음 |
| 없어도 되는가 | 아니다. 나머지 둘의 전제 | 예. F1 수기 입력으로 대체 가능 | 예. F1은 F3에 의존하지 않는다 (F1-AG-07) |

> **[주의]** **경계가 무너지는 지점을 미리 정한다.** ① F1은 전사 결과를 받고 저장할 뿐, 무엇이 임차인 성명인지 **판정**하는 책임은 F2에 있다. 다만 F2가 판정하지 못한 것을 **사람이 메우는 화면**은 F1이 제공한다 (F1-ST-09). ② F3의 출력이 F1의 데이터가 되는 것은 F1에 AI가 붙는 것이 아니다. 중개 판정이 임장 일정을 제안하고 중개사가 승인하면 F1에 일정이 생기며, 그 일정이 외부 캘린더로 나가는 것은 F1의 출력 채널이다.

### 0.4 세 기능이 공유하는 원칙

| # | 원칙 | 근거 | 적용 |
|---|---|---|---|
| 1 | **장부는 세대 전수 대장이다** | 현행 장부는 101동 101호부터 매물 여부와 무관하게 전 세대가 행으로 존재한다. 최상위 단위는 매물이 아니라 세대이며 매물화는 세대의 일시적 상태다 | F1 1.3 · F2 6.1 · F3 5장 |
| 2 | **기존 업무 흐름을 바꾸지 않는다** | 현행 장부의 조작 순서·용어·로그 포맷을 그대로 따른다. 새 UI를 강요하면 도입되지 않는다 | 전 부 |
| 3 | **데이터는 지우지 않는다** | 2018년 상담 기록까지 삭제 없이 누적한다. 이 누적이 F3 대리 에이전트의 자산이다 | F1 1.3 · F3-LA-05 · F3-TL-01 |
| 4 | **AI 결과는 승인 전 확정되지 않는다** | 사용자가 확인하고 저장해야 장부에 반영된다 | F2 1장 · F1-ST-11 · F3-CM-03 |
| 5 | **근거 없는 값을 만들지 않는다** | F2는 음성에 없는 값을 추측하지 않고, F3는 근거 원문이 없으면 「추정」으로 표시한다 | F2 5.4 · F3-CM-02 |
| 6 | **기존 값을 자동으로 덮어쓰지 않는다** | AI는 원칙적으로 빈 필드만 채운다. 상담 로그는 추가 전용이다 | F1-LG-01 · F1-ST-06/07 · F2-REV-02 |
| 7 | **작성 주체를 구분해 남긴다** | 사람 / F2 / F3가 만든 로그·필드·일정을 구분 표시한다 | F1-LG-11 · F1-AG-04 · F2-REV-04 · F3-IF-05 |

#### F2 ↔ F3 — 직접 접점 없음

F2와 F3는 서로를 호출하지 않는다. F2가 만든 상담 로그는 F1에 저장되고, F3는 그 로그를 F1에서 읽는다. **연결은 언제나 F1을 경유한다.**

> **[참고]** **이 구조가 주는 것.** F2가 만든 로그의 품질이 F3 판정의 품질을 결정한다. 「급하지 않음」 「본인 집이 팔려야 살 수 있다」 같은 비구조화 진술이 로그에 남아야 F3의 대리 에이전트가 조건표 너머를 읽을 수 있다. F2의 상담 로그 초안 생성(F2-REV-04)은 입력 편의 기능이 아니라 **F3의 원료 공급 장치**다.

### 0.6 통합 용어

세 부에서 공통으로 쓰는 용어. 각 부의 고유 용어는 해당 부의 용어 절을 따른다.

| 용어 | 정의 | 정의 위치 |
|---|---|---|
| 세대 | 단지 내 개별 호실. 매물 여부와 무관하게 존재하는 장부의 기본 단위 | 제1부 2.1 |
| 매물 | 세대가 거래 대상이 된 상태. 세대에 종속되며 소멸·재생성될 수 있다 | 제1부 2.1 |
| 매물장 · 세대전체장부 | 세대 전수 대장. 현행 장부의 기본 화면 | 제1부 2.1 · 제2부 2 |
| 구입장 · 손님대장 | 손님(수요) 대장 | 제1부 2.1 · 제2부 2 |
| 상담 로그 | `[YY-MM-DD HH:MM 주①]본문` 포맷의 append 텍스트 | 제1부 2.1 · 7장 |
| 인물 인덱스 | 로그·연락처의 `①②③`. 같은 역할에 인물이 여러 명일 때의 순번 (남편 ①, 아내 ②) | 제1부 2.1 · 7.1 |
| 현상태 / 현매물 / 명도 / 경신 / 월환 / 붙박이 | 현업 표기. 시스템이 데이터와 함께 보관해야 할 정보 | 제1부 2.1 · 14장 |

| 포지션 카드 | 대리 에이전트의 출력 규격. 당사자 한 명의 실제 입장 | 제3부 4장 |
| 앵커 / 후보 | 판정 기준이 되는 한쪽 카드 / 반대편에서 조회된 대상 | 제3부 2.1 |
| 교차 판정 / 배치 판정 | 앵커 1:후보 N 인라인 판정 / 같은 쪽 N건 배치 판정 | 제3부 2.1 · 10장 · 11장 |

### 0.8 AI 사용 구조

| 구분 | F2 | F3 |
|---|---|---|

## 제1부 F1 장부 시스템

> **원본 문서** — `F1_요구사항정의서_5차수정.md` · 원제 「F1 장부 시스템 요구사항 정의서」

> 현재 사용 중인 장부 도구의 기능을 웹으로 이전한다. 기술적으로 불가한 항목만 제외한다.

### 1. 개요

#### 1.1 목적

본 문서는 F1 장부 시스템이 충족해야 할 요구사항을 정의한다. F1은 F2(STT 입력)와 F3(비서 에이전트)가 읽고 쓰는 **데이터 기반**이며, F1이 현업 수준의 완결성을 갖지 못하면 나머지 두 기능은 시연 이상의 의미를 갖지 못한다.

#### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | 매물장(세대 전수 대장) · 구입장(손님 대장) · 상담 로그 · 세대/손님 상세 · **상태 전이 및 거래 이력** · **문서함** · 검색 · 문자 대상 수집 및 **문자 작성·발송 흐름(개인·단체)** · **F2·F3 연동 접점** · 일정 · **알림** · 마스터 데이터 · 권한 · **사용법 가이드** |
| 제외 | 전화 발신 및 통화 이력 연동 · `tel:` 링크 · SMS 실발송 · 원격제어 · 도움말 동영상 · **현행 장부 데이터 이관** (16장 참조) |
| 유보 | SMS 실발송은 **현 범위에서 제외하되 추후 활성화 가능한 구조**로 설계한다. 발신번호 사전등록 등 법적 요건 충족 시 설정 전환만으로 켠다 (F1-MS-14) |
| 타 기능 경계 | 음성 인식 자체는 F2, 판단·브리핑은 F3. F1은 **저장과 조회**, 그리고 **F2 결과를 받는 화면과 규칙**을 책임진다 (9장) |

#### 1.3 설계 원칙

> **[참고]** **원칙 1 — 장부는 세대 전수 대장이다.** 현행 장부의 기본 화면은 101동 101호부터 매물 여부와 무관하게 전 세대가 행으로 존재한다. 중개사는 매물을 관리하는 것이 아니라 **단지 전 세대를 대상으로 접촉 이력을 누적**한다. 최상위 단위는 매물이 아니라 세대이며, 매물화는 세대의 일시적 상태다.

> **[참고]** **원칙 2 — 기존 업무 흐름을 바꾸지 않는다.** 현행 장부의 조작 순서·용어·로그 포맷을 그대로 따른다. 새 UI를 강요하면 도입되지 않는다. 개선은 **제약을 없애는 방향**으로만 한다.

> **[참고]** **원칙 3 — 데이터는 지우지 않는다.** 현행 장부는 2018년 상담 기록까지 삭제 없이 누적한다. 이 누적이 F3 조사관의 자산이다.

> **[범례]** 필수 없으면 현업 사용 불가 권장 있어야 실용적 선택 여유 시 **출처** 매물장 / 구입장 / 세대상세 / 손님입력 = 현행 장부 화면. 인터뷰 / 신규 = 그 외

### 9. F2 · F3 연동

음성 인식은 F2, 판단·브리핑은 F3의 책임이다. 본 장은 **두 기능이 F1에 닿는 접점**만 정의한다.

> **[참고]** **실행 지점이 두 곳이다.** STT 버튼은 ① **F1 매물장 그리드 화면**과 ② **특정 행을 선택해 연 상세 로그 팝업** 양쪽에 존재한다. 그리드에서 실행할 때는 **행을 선택했으면 그 행이, 선택하지 않았으면 새로 만든 행이** 대상이 된다 — 어느 쪽도 실행을 막지 않는다. 경로가 둘이어도 **결과는 같은 로그 레코드로 수렴**해야 하며, 반영 규칙과 **표시 방식(비동기 팝업)**도 동일해야 한다.

#### 9.1 실행 경로

| ID | 요구사항 | 상세 | 등급 | 출처 |
|---|---|---|---|---|
| F1-ST-01 | 버튼 이원 배치 | STT 실행 버튼을 **매물장 그리드 화면**과 **상세 로그 팝업** 양쪽에 제공한다. 구입장에도 동일하게 적용한다 | 필수 | 신규 |
| F1-ST-15 | 결과 표시는 팝업 | F2 버튼을 누르면 **비동기 팝업창**이 뜬다. **화면을 자동 스크롤해 하단에 상세 로그창을 펼치지 않는다** (F1-LG-19). 팝업은 F1-LG-15와 **같은 창**이다. 음성메모 입력은 이 상세 팝업 위에 겹치는 **별도 팝업**으로 열린다 (F2-POP-03) | 필수 | 신규 |
| F1-ST-02 | 그리드 실행 — 기존 행 선택 | 행을 선택한 상태에서 실행하면 **해당 행**이 대상이 된다. 복수 행이 선택된 상태에서는 실행할 수 없다 (대상 1건 원칙) | 필수 | 신규 |
| F1-ST-16 | 그리드 실행 — 행 미선택 | **선택된 행이 없으면 실행을 막지 않고 신규 행을 추가**한다. F1-GR-30의 빈 행을 생성하고 그 행을 대상으로 삼아 팝업을 연다. 기존 값이 없으므로 변경 판단(F1-ST-06)이 발생하지 않는다 | 필수 | 신규 |

| F1-ST-18 | 미저장 신규 행 정리 | 신규 행에서 실행한 뒤 저장하지 않고 닫으면 F1-GR-32에 따라 확인 후 그 행을 남기지 않는다. 전사 원문은 재시도할 수 있도록 세션 내에 보관한다 | 필수 | 신규 |
| F1-ST-03 | 그리드 실행 — 반영 대상 | 전사 결과를 **해당 행의 필드**와 **해당 세대의 상담 로그** 양쪽에 반영한다. 로그만 남고 필드가 비는 상태를 만들지 않는다 | 필수 | 신규 |
| F1-ST-04 | 상세 로그 실행 — 대상 고정 | 상세 로그 팝업에서 실행하면 해당 세대·손님이 **대상으로 고정**되며 변경할 수 없다. 결과는 해당 상담 로그에 반영한다 | 필수 | 신규 |
| F1-ST-05 | 누락 정보 기입 의무 없음 | 신규 행이든 기존 행이든 **누락 항목이 있어도 저장을 막지 않는다**. 미입력 항목은 「미확인」으로 표시해 나중에 찾을 수 있게 한다 (F1-ST-09) | 필수 | 신규 |

|---|---|---|---|---|

> **[주의]** **경계** — F1은 전사 결과를 **받고 저장**할 뿐, 무엇이 임차인 성명인지 판정하는 책임은 F2에 있다. 다만 **F2가 판정하지 못한 것을 사람이 메우는 화면**은 F1이 제공해야 한다 (F1-ST-09). 이 경계가 무너지면 두 기능의 책임이 섞인다.

#### 9.3 F3 연동 접점

> **[참고]** **F3는 F1을 읽는다.** F2의 접점은 화면이지만 **F3의 접점은 데이터**다. F3가 무엇을 어떤 권한으로 읽고 어디에 쓸 수 있는지가 정해지지 않으면, F1은 완성되어도 F3를 붙일 수 없다.

| ID | 요구사항 | 상세 | 등급 | 출처 |
|---|---|---|---|---|
| F1-AG-01 | 조회 인터페이스 | F3가 세대·손님·상담 로그·일정·거래 이력을 조회할 수 있는 **읽기 인터페이스**를 제공한다. 화면 스크래핑이 아니라 정의된 계약이어야 한다 | 필수 | 신규 |
| F1-AG-02 | 변경분 조회 | 「특정 시점 이후 바뀐 레코드」를 가져올 수 있어야 한다. 매번 전량을 읽는 구조는 7,200행 이상에서 성립하지 않는다 | 필수 | 신규 |
| F1-AG-03 | 쓰기 범위 제한 | F3가 쓸 수 있는 대상은 **상담 로그 추가 · 일정 등록**으로 한정한다. 세대·손님의 기존 필드를 F3가 직접 수정하지 못한다 | 필수 | 신규 |
| F1-AG-04 | 작성 주체 구분 | F3가 만든 로그·일정은 사람·F2가 만든 것과 구분 표시한다. F1-LG-11의 AI 생성 플래그를 **주체별로 확장**한다 (사람 / F2 / F3) | 필수 | 신규 |
| F1-AG-05 | 개인정보 최소 전달 | F3에 전달하는 데이터에서 **연락처·생년월일은 기본 마스킹**한다. 필요한 경우에만 명시적으로 요청·기록한다 | 필수 | 신규 |
| F1-AG-06 | 접근 감사 | F3의 조회·쓰기를 전량 기록한다. 사람의 접근 감사(F1-SE-07)와 같은 곳에 남긴다 | 필수 | 신규 |
| F1-AG-07 | F3 없이 동작 | F3가 연결되지 않았거나 응답하지 않아도 F1의 모든 기능은 정상 동작해야 한다. F1은 F3에 의존하지 않는다 | 필수 | 신규 |

## 제2부 F2 STT 음성 입력

> **원본 문서** — `F2_REQUIREMENTS_DEFINITION_V3.md` · 원제 「F2 MVP 기능 요구사항 정의서」

F1 행 상세 팝업 안에서 음성메모를 받아 빈 필드와 상담 로그 초안을 만든다. 별도 화면이 아니라 F1의 입력 보조다.


### 1. 기능 정의

> F2는 F1 장부에 새 행을 추가한 뒤, 해당 행의 상세 팝업에서 음성메모를 입력하면 RunPod Whisper와 로컬 LLM이 내용을 분석하여 행의 빈 필드와 상담 로그 초안을 생성하고, 사용자의 확인을 거쳐 장부에 반영하는 기능이다.

```text
장부 선택 → 행 추가 → 행 상세 팝업 → [음성메모 입력] → 음성메모 팝업
→ 주의 문구 확인 → 음성 파일 업로드 → RunPod Whisper STT → 로컬 LLM 분류·슬롯 필링
→ 빈 필드 채우기 제안 → 사용자 확인·수정 → 상세 팝업에 반영 → 장부 저장
```

#### 핵심 원칙

- F2는 별도 메뉴나 독립 화면을 갖지 않는다. **F1 행 상세 팝업에서 호출하는 하위 팝업**으로 실행한다 (F2-POP-03).
- AI 결과는 장부에 바로 반영하지 않고 먼저 채우기 제안으로 표시한다.
- AI는 원칙적으로 **선택한 행의 빈 필드만 채운다.**
- 기존 값은 자동으로 덮어쓰지 않는다.
- 사용자가 확인하고 저장해야 최종 장부에 반영된다.
- 음성메모의 핵심 내용은 해당 행의 상담 로그에도 추가한다.

---

### 2. 적용 장부

| 장부 | 역할 | 대표 상담 유형 |
|---|---|---|
| 세대전체장부·매물장 | 세대와 매물 정보 관리 | 매도의뢰 |
| 손님대장·구입장 | 고객의 매수·전세·월세 조건 관리 | 매수문의 |

공동중개와 단순문의로 분류된 메모는 행의 필드를 임의로 채우지 않고 상담 로그만 작성할 수 있다.

---

### 3. 전체 사용자 흐름

#### 3.1 신규 행 작성

1. 사용자가 `매물장` 또는 `구입장`을 선택한다.
2. 사용자가 상단 메뉴의 `행 추가`를 누른다.
3. 선택한 장부에 상태가 `임시저장`인 빈 행을 생성한다.
4. 생성된 행의 상세 팝업을 자동으로 연다.
5. 사용자는 직접 값을 입력하거나 F2 음성 채우기를 실행한다.

#### 3.2 F2 음성 채우기

1. 상세 팝업의 `음성메모 입력`을 눌러 별도 팝업을 열고, 주의 문구를 확인한 뒤 파일을 선택한다.
2. 사용자가 `분석 실행`을 누른다.
3. 음성을 RunPod Whisper로 전송한다.
4. 반환된 STT 텍스트를 로컬 LLM이 분석한다.
5. 상담 유형, 장부 필드, 상담 로그 초안을 생성한다.
6. 팝업에 현재값과 AI 제안값을 비교해 표시한다.
7. 사용자가 제안을 선택·수정한 후 `선택 항목 반영`을 누른다.
8. 반영된 값을 최종 확인하고 `장부 저장`을 누른다.

### 4. 장부 목록 화면 요구사항

#### F2-LIST-01. 행 추가

- 각 장부 화면에 `행 추가` 버튼을 제공한다.
- 버튼을 누르면 현재 선택한 장부에 빈 행을 한 건 생성한다.
- 새 행에는 내부 행 ID, 작성자, 생성 시각, 상태를 자동 부여한다.
- 행 상태는 `임시저장`으로 표시한다.
- 행 생성 직후 해당 행의 상세 팝업을 자동으로 연다.

#### F2-LIST-02. 행 선택

- 사용자가 장부의 행을 한 번 누르면 해당 행의 상세 팝업을 연다.
- 팝업에는 선택한 행의 모든 상세 필드와 상담 로그를 표시한다.
- 사용자가 팝업을 닫아도 저장된 값은 목록 행에 반영되어야 한다.

#### F2-LIST-03. 행 저장 상태

장부 목록에서 행별 저장 상태를 확인할 수 있어야 한다. **상태는 아래 둘뿐이며 AI 처리 상태를 목록 컬럼으로 두지 않는다.**

| 상태 | 의미 |
|---|---|
| 임시저장 | 행이 생성·수정되었으나 최종 저장되지 않음 |
| 저장 완료 | 사용자가 확인하고 장부에 저장함 |

STT·로컬 LLM의 진행 상태(업로드 중 · 변환 중 · 분석 중 · 실패)는 실행 중인 음성메모 팝업(F2-POP-03) 안에서만 표시하고 장부 목록으로 올리지 않는다. 분석이 실패해도 행의 저장 상태는 바뀌지 않는다.

#### F2-LIST-04. 미완성 행 처리

- 필수 필드가 비어 있는 행은 `임시저장`으로 유지한다.
- 미완성 행이 존재하면 목록에서 구분해 표시한다.
- 사용자는 미완성 행을 다시 열어 이어서 작성하거나 삭제할 수 있다.

### 5. 행 상세 팝업 요구사항

#### 5.1 팝업 기본 구조

```text
┌──────────────────────────────────────────────────────┐
│ 행 제목 · 저장 상태                            [닫기] │
├──────────────────────────────────────────────────────┤
│ 장부 상세 정보 — 33개 항목 전부                        │
│ 각 필드의 현재값 / 직접 입력                           │
│                              [음성메모 입력]           │
│                              [관계 수정]               │
├──────────────────────────────────────────────────────┤
│ 상담 로그                                             │
├──────────────────────────────────────────────────────┤
│ [임시저장] [행 삭제] [장부 저장]                       │
└──────────────────────────────────────────────────────┘

   [음성메모 입력] → 상세 팝업 위에 겹치는 별도 팝업 (F2-POP-03)
   ┌────────────────────────────────────────────┐
   │ 개인정보 주의 문구 · 확인                    │
   │ 파일 선택 / 재생 / 분석 실행                 │
   │ STT · AI 분석 진행 상태                      │
   │ AI 제안값 검토표                             │
   │ [선택 항목 반영] [닫기]                      │
   └────────────────────────────────────────────┘
```

#### F2-POP-01. 상세정보 표시

- 선택한 행의 전체 필드를 표시한다.
- 각 필드는 사용자가 직접 수정할 수 있어야 한다.
- 빈 필드는 `미입력` 상태로 구분한다.
- AI가 제안한 필드는 제안값과 근거 문장을 함께 표시한다.

#### F2-POP-02. 닫기

- 저장하지 않은 변경사항이 있으면 닫기 전에 확인창을 표시한다.
- `계속 작성`, `임시저장 후 닫기`, `변경 취소` 중 하나를 선택할 수 있어야 한다.

#### F2-POP-03. 음성메모 별도 팝업

- 상세 팝업의 `음성메모 입력`을 누르면 **상세 팝업 위에 겹치는 별도 팝업**이 열린다. 상세 팝업 안의 영역이 아니다.
- 이 팝업 안에서 주의 문구 확인 · 파일 업로드 · 분석 실행 · 제안값 검토를 모두 수행한다.
- `선택 항목 반영`을 누르면 팝업이 닫히면서 **부모 상세 팝업의 입력칸에 값이 채워진다.** 이 시점에도 장부 저장은 일어나지 않는다.
- 음성메모 팝업을 닫아도 **부모 상세 팝업의 미저장 입력값은 유지**된다.
- 상세 팝업 1건당 음성메모 팝업은 하나만 열 수 있으며, 분석 중 중복 실행을 막는다.

---

#### 5.2 F2 음성메모 입력 영역

#### 입력 기능

| 기능 | 동작 |
|---|---|
| 파일 선택 | `wav`, `mp3`, `m4a` 파일 업로드 |
| 음성 재생 | 분석 전 입력 음성 확인 |
| 파일 교체 | 선택한 파일을 지우고 다른 파일을 올린다 |
| 분석 실행 | RunPod STT와 로컬 LLM 분석 시작 |

**브라우저 내 직접 녹음 기능은 제공하지 않는다.** 사용자가 자신의 기기에서 남긴 음성메모 파일을 업로드하는 경로만 지원한다.

#### 개인정보 주의 문구

음성메모 팝업(F2-POP-03) 진입 시 아래 주의 문구를 표시하고, 사용자가 **확인에 체크해야 파일 선택이 활성화**된다. 개인정보 활용 동의를 받는 것과 같은 형식이다.

> 실제 고객 통화를 업로드하지 말고, 상담 후 장부에 필요한 내용만 음성메모로 남겨주세요. 주민등록번호, 계좌번호, 비밀번호 등 불필요한 민감정보는 입력하지 마세요.

- **주의 문구 표시와 확인 체크가 전부다.** 업로드한 음성이나 전사 결과를 검사해 수정 안내를 띄우지 않으며, 그 사유로 저장을 막지 않는다.
- 확인 체크 여부와 시각을 기록한다.

#### 실행 조건

- 업로드한 파일이 있어야 한다.
- 개인정보 주의 문구를 확인하지 않으면 파일 선택과 분석 실행을 활성화하지 않는다.
- 지원하지 않는 형식, 빈 음성, 제한을 초과한 파일은 실행할 수 없다.
- 처리 중에는 `분석 실행` 버튼을 비활성화하여 중복 요청을 방지한다.
- 분석 중 팝업을 닫으려 하면 처리 취소 여부를 확인한다.

#### 5.3 STT 처리 요구사항

#### 처리 과정

1. 음성을 암호화된 통신으로 RunPod에 전송한다.
2. RunPod에 직접 배포한 Whisper가 STT 텍스트를 생성한다.
3. 생성된 텍스트만 F1 서버로 반환한다.
4. 성공·실패 여부와 관계없이 RunPod의 임시 음성을 삭제한다.
5. 반환된 텍스트를 로컬 LLM에 전달한다.

#### 화면 표시

- `음성 업로드 중`
- `텍스트 변환 중`
- `장부 정보 분석 중`
- `분석 완료`
- `분석 실패`

#### 보안 조건

- RunPod 로그에 음성 원본, STT 전문, 개인정보를 기록하지 않는다.
- RunPod에 음성 또는 STT 텍스트를 영구 저장하지 않는다.
- 장부의 기존 데이터는 RunPod에 전달하지 않는다.
- 로컬 LLM에는 STT 텍스트와 현재 장부 종류만 전달한다.

#### 실패 처리

- 네트워크 오류: 동일 음성으로 `다시 시도` 제공
- STT 실패: `다시 변환` 또는 `다른 파일 업로드` 제공
- 빈 텍스트: AI 분석을 중단하고 다른 파일 업로드를 안내
- 로컬 LLM 실패: STT 텍스트는 유지하고 `분석 다시 실행` 제공

---

#### 5.4 로컬 LLM 분석 요구사항

로컬 LLM은 다음 작업만 수행한다.

1. 상담 유형 분류: 매도의뢰·매수문의·공동중개·단순문의
2. 현재 장부와 상담 유형이 맞는지 확인
3. 현재 장부의 필드에 맞춰 값 추출
4. 상담 로그 초안 생성
5. 누락·변경·불명확한 값 표시
6. 각 제안값의 근거 문장 제공

#### 장부 불일치

- 매물장 행에서 `매수문의`가 감지되면 필드를 자동 반영하지 않는다.
- 구입장 행에서 `매도의뢰`가 감지되면 필드를 자동 반영하지 않는다.
- 팝업에 `현재 장부와 상담 유형이 다릅니다` 경고를 표시한다.
- 사용자는 상담 로그만 저장하거나 올바른 장부에서 새 행을 만들 수 있다.

#### 생성 금지

- 음성에 없는 값을 추측하지 않는다.
- 불명확한 숫자·날짜·동·호를 확정값으로 만들지 않는다.
- 여러 값이 서로 다르면 임의 선택하지 않는다.
- 기존 장부 값을 자동으로 덮어쓰지 않는다.

### 6. 장부별 AI 채우기 필드

#### 6.1 매물장·세대전체장부

AI는 음성에서 확인되는 경우 다음 빈 필드를 제안한다.

| 구역 | 필드 |
|---|---|
| 식별 | 단지, 평형, 동, 호, 타입, 방향 |
| 현 임대차 | 현상태, 현재 보증금·차임, 융자, 만기일 |
| 매물화 | 접수일, 현매물, 진행상태, 명도 조건 |
| 가격 | 매매가, 전세보증금, 월세 보증금·차임 |
| 스펙 | 확장 여부, 붙박이, 시설 상태 |
| 인적 | 임대인, 임대인 전화, 임차인, 임차인 전화, 관련 중개업소 |
| 관리 | 담당자, 비고 |

#### 최소 저장 조건

- 단지
- 동
- 호

동·호가 미확인인 경우 사용자가 `미확인 상태로 임시저장`할 수 있지만 저장 완료 상태로 확정할 수는 없다.

#### 중복 검사

단지·동·호가 기존 행과 동일하면 신규 저장을 중단하고 기존 행 열기를 제안한다.

#### 6.2 구입장·손님대장

AI는 음성에서 확인되는 경우 다음 빈 필드를 제안한다.

| 구역 | 필드 |
|---|---|
| 접수 | 접수일, 최종접촉일 |
| 희망 조건 | 거래 구분, 희망 단지, 평형, 금액 원문, 이사일 원문 |
| 인적 | 구입자 이름·별칭, 전화번호, 관련 중개업소 |
| 진행 | 진행단계, 완료 여부 |
| 관리 | 담당자, 분류, 비고, 개인정보 동의 여부 |

#### 최소 저장 조건

- 구입자 이름 또는 업무용 별칭
- 거래 구분
- 희망 단지·지역 또는 희망 평형 중 하나
- 금액 조건

전화번호와 개인정보 동의 여부는 사용자가 직접 확인해야 하며 AI가 동의 여부를 임의로 `동의` 처리할 수 없다.

### 7. AI 제안값 검토 및 반영

#### F2-REV-01. 제안 목록

각 제안은 다음 정보를 표시한다.

| 항목 | 내용 |
|---|---|
| 반영 선택 | 해당 제안을 적용할지 체크 |
| 필드명 | 값이 들어갈 장부 칸 |
| 현재값 | 현재 행에 저장된 값 |
| AI 제안값 | 음성에서 추출한 값 |
| 상태 | 확인됨·확인 필요·변경·누락 |
| 근거 | 해당 값이 나온 STT 문장 |

#### F2-REV-02. 빈 필드 반영

- 현재값이 비어 있으면 AI 제안값을 기본 선택한다.
- 현재값이 존재하면 기본적으로 반영하지 않는다.
- 기존 값과 다른 제안은 `변경`으로 표시한다.
- 기존 값을 바꾸려면 사용자가 직접 `기존 값 변경`을 선택해야 한다.
- 변경 전 값, AI 제안값, 사용자 최종값을 이력으로 남긴다.

#### F2-REV-03. 선택 항목 반영

- `선택 항목 반영`을 누르면 체크한 제안만 상세 입력칸에 채운다.
- 이 단계에서는 아직 최종 장부 저장을 수행하지 않는다.
- 사용자는 반영된 값을 다시 직접 수정할 수 있다.

#### F2-REV-04. 상담 로그

AI는 다음 형식의 상담 로그 초안을 생성한다.

- 상담 일시
- 상담 유형
- 핵심 상담 내용
- 확정된 조건
- 미확정·추가 확인 사항

사용자는 상담 로그를 수정하거나 제외할 수 있다. 장부 저장 시 승인된 로그를 해당 행의 상담 이력에 추가하고 `F2 생성` 표시를 남긴다.

### 8. 저장 요구사항

#### 임시저장

- 현재 입력값과 AI 제안값을 보존한다.
- 행 상태를 `임시저장`으로 유지한다.
- 장부 목록에서 다시 열어 이어서 작성할 수 있다.

#### 장부 저장

1. 장부별 최소 저장 조건을 검사한다.
2. `변경` 상태의 필드에 대해 사용자가 반영 여부를 선택했는지 검사한다.
3. 매물장은 단지·동·호 중복을 검사한다.
4. 사용자 최종 확인 시각과 확인자를 기록한다.
5. 필드와 상담 로그를 저장한다.
6. 행 상태를 `저장 완료`로 변경한다.
7. 팝업을 닫고 목록의 해당 행을 갱신한다.

#### 저장 실패

- 입력값, STT 결과, AI 제안값을 유지한다.
- 실패 원인과 `다시 저장` 버튼을 표시한다.
- 중복 저장을 방지하기 위해 동일 요청 ID를 다시 사용한다.

### 9. MVP 제외 범위

- 실제 고객 통화 자동 녹음
- **브라우저 내 직접 녹음** (파일 업로드만 지원한다)
- 화자 분리
- 사용자 확인 없는 자동 저장
- 기존 행 전체를 AI가 자동 수정하는 기능
- 계약서 자동 작성
- 법률 판단 및 가격 평가
- 고객에게 메시지를 자동 발송하는 기능
- 공동중개·단순문의로 신규 장부 행을 자동 생성하는 기능

### 10. MVP 완료 기준

- 매물장과 구입장에서 `행 추가`로 빈 행을 만들 수 있다.
- 신규 행 생성 직후 상세 팝업이 열린다.
- 기존 행을 누르면 동일한 상세 팝업이 열린다.
- 상세 팝업의 [음성메모 입력]을 누르면 별도 팝업이 열리고 그 안에서 음성 파일을 업로드할 수 있다.
- RunPod Whisper가 STT 텍스트를 반환하고 임시 음성을 삭제한다.
- 로컬 LLM이 상담 유형과 현재 장부의 필드값을 추출한다.
- AI 제안값과 현재값을 팝업에서 비교할 수 있다.
- AI가 빈 필드만 기본 반영 대상으로 선택한다.
- 기존 값은 사용자 선택 없이 덮어쓰지 않으며, 별도의 충돌 확인 화면 없이 검토표에서 결정한다.
- 선택한 제안만 상세 필드에 반영할 수 있다.
- 사용자가 반영값을 수정하고 최종 저장할 수 있다.
- 상담 로그가 선택한 행에 연결된다.
- 저장 후 목록 행이 즉시 갱신된다.
- 실패해도 작성 중인 내용이 사라지지 않는다.

### 1. 개요

#### 1.1 목적

본 문서는 F3 비서 에이전트가 충족해야 할 요구사항을 정의한다. F3는 F1이 누적한 **구조화 데이터와 상담 로그**를 읽어 당사자의 실제 입장을 판정하고, 양측 입장을 붙여 거래 가능성과 행동을 제안한다.

조건표 매칭은 SQL이면 된다. F3가 존재하는 이유는 **조건표에 들어가지 않은 말**에 있다. 매물장에는 매매가 21.5억이 적혀 있지만 같은 세대의 로그에는 "급하지 않음"이 적혀 있고, 구입장에는 예산 28억이 적혀 있지만 같은 손님의 로그에는 "한 군데 더 상담"이 적혀 있다. 중개사의 실력은 조건표를 맞추는 것이 아니라 **양쪽이 말한 것 중 조건표에 안 들어간 것을 기억해서 붙이는 것**이며, F3는 그 작업을 대행한다.

#### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | 포지션 카드 생성 · 매물 대리 · 손님 대리 · 중개 판정 · 교차 판정(인라인) · 배치 판정(캠페인) · 문안 생성 · 신뢰 루프 · F1 연동 규약 |
| 제외 | 날짜 계산 · 조건 검색 · 목록 조회 · 일정 데이터 저장 · 캘린더 동기화 · 규칙 알림 · 정책 학습 · 시세 폴링 · 스케줄 배치 (17장) |
| 유보 | 배치 판정의 교차 옵션(11.4)은 구조만 확보하고 MVP 구현 대상에서 제외한다 |
| 타 기능 경계 | 저장·조회·화면은 F1, 음성 인식은 F2. F3는 **판단과 제안**만 책임진다. F3의 출력이 F1 데이터가 되는 것은 F1에 AI가 붙는 것이 아니다 |

#### 1.3 설계 원칙

> **[참고]** **원칙 1 — 대리는 서로의 로그를 읽지 않는다.** 매물 대리는 집주인이 한 말만, 손님 대리는 손님이 한 말만 읽는다. 섞으면 누가 무엇을 말했는지 흐려지고, 하나의 프롬프트에서 두 입장을 동시에 옹호하게 하면 중립적으로 뭉개진다. 위계는 중개 판정의 **기각 권한**에서 생긴다.

> **[참고]** **원칙 2 — 근거 없는 단정을 금지한다.** 모든 판정 항목에 로그 원문이 붙거나 「추정」으로 표시된다. 대리가 엉뚱한 포지션을 두 번 세우면 아무도 보지 않는다. 틀릴 수 있다는 전제 위에 설계한다.

> **[참고]** **원칙 3 — 컷이 없다.** 판정한 후보 전부를 등급별로 보여주고, 기각 건도 사유와 함께 접어서 노출한다. 무엇을 왜 걸렀는지 검증 가능해야 한다. 상한이 필요한 곳은 컷이 아니라 **페이징**으로 처리한다.

> **[참고]** **원칙 4 — 정기 실행이 없다.** F3는 사용자 행동에만 반응한다. 아침 브리핑을 유지하려면 브리핑만을 위한 장치(쿼터·편성·상한·이월 큐)가 계속 필요했고, 이는 사용자 가치가 아니라 설계가 자초한 부채였다. 브리핑에 넣으려던 항목은 F1(캘린더·그리드 정렬·규칙 알림)과 교차 판정·배치 판정으로 재배치한다.

> **[범례]** 필수 없으면 F3의 존재 이유가 성립하지 않음 · 권장 있어야 실용적 · 선택 여유 시 · P2 구조만 확보하고 구현 유보
> **[출처]** 설계서 = F3 설계서 v4 / F1 = F1 요구사항 정의서 / 인터뷰 / 신규

### 2. 용어 및 구성

#### 2.1 용어 정의

| 용어 | 정의 |
|---|---|
| 포지션 카드 | 대리 에이전트의 출력 규격. 당사자 한 명(또는 한 세대)의 실제 입장을 구조화한 것. 중개 판정의 입력이자 캐시 단위 |
| 매물 대리 | 세대·매물 보유자의 입장을 세우는 에이전트. 팔거나 세놓는 쪽을 대변 |
| 손님 대리 | 구입장 손님의 매수·임차 입장을 세우는 에이전트. 사거나 들어가는 쪽을 대변 |
| 중개 판정 | 앵커 1장과 후보 N장을 한 번에 받아 등급·순위·행동을 정하는 에이전트. 기각 권한을 가진다 |
| 앵커 | 판정의 기준이 되는 한쪽 포지션 카드 1장 |
| 후보 | 앵커의 반대편에서 조회된 대상. 후보 추출은 SQL이며 에이전트가 아니다 |
| 교차 판정 | 앵커 1 : 후보 N 형태. 저장·조회 시 화면에 즉시 붙는다. 세 에이전트를 모두 쓴다 |
| 배치 판정 | 같은 쪽 대상 N장을 대리 하나로 N회 판정하는 형태. 반대편이 없으므로 중개 판정을 쓰지 않는다 |
| 조건 세그먼트 | 장부 값으로 뽑히는 대상 집합. SQL. 예 — 만기 3개월 이내, 6개월 미접촉 |
| 판정 세그먼트 | 로그를 읽어야 나오는 대상 집합. 대리 에이전트. 예 — 최근 명시적으로 거절한 사람 |
| 날짜 신호 | 만기 D-day·이사일·최종 접촉 후 경과 등 SQL로 산출해 대리의 입력으로 넣는 값. 그 자체가 출력이 되지 않는다 |
| 등급 | 중개 판정의 결과값. 강함 / 약함 / 기각 |

### 4. 포지션 카드

두 대리의 출력 규격이자 중개 판정의 입력. 캐시 단위이기도 하다.

#### 4.1 규격

```text
{
  target        : { side: "매물" | "손님", id, label }
  generated_at  : 생성 시각
  source        : { log_count, last_log_at, data_version }
  intent        : { value: 있음 | 없음 | 불명 | 철회,
                    evidence: 원문 인용, log_ref: 로그 ID }
  price         : { stated: 장부 표기값,
                    estimated: 대리 추정값,
                    basis: 추정 근거 원문 | null }
  urgency       : { value: 급함 | 보통 | 여유 | 불명, evidence }
  timing        : { constraints: [명도·만기·이사일 등],
                    hard_deadline: 실질 마감일 | null }
  flexible      : [ 양보 가능 조건 ]
  inflexible    : [ 양보 불가 조건 ]
  contactability: { status: 양호 | 주의 | 불가,
                    note: "통화 어려움, 문자 선호" }
}
```

| ID | 요구사항 | 상세 | 등급 | 출처 |
|---|---|---|---|---|
| F3-PC-01 | 카드 스키마 준수 | 두 대리는 위 규격의 항목을 모두 채워 출력한다. 판단이 불가한 항목은 비우지 않고 `불명`으로 표시한다 | 필수 | 설계서 |
| F3-PC-02 | 근거 원문 부착 | `intent` · `urgency`는 로그 원문 인용과 로그 ID를 함께 반환한다. 인용이 없으면 「추정」으로 표시한다 | 필수 | 설계서 |
| F3-PC-03 | 추정가 근거 의무 | `price.estimated`가 `price.stated`와 다르면 `basis`에 근거 원문을 반드시 채운다. 근거 없는 추정가는 반환하지 않는다 | 필수 | 설계서 |
| F3-PC-04 | 실질 마감일 산출 | `timing.hard_deadline`은 잔금·이사일·만기에서 역산한 **실질 마감**을 넣는다. 날짜 산수는 코드가 계산해 입력으로 넣는다 (F3-SQ-05) | 필수 | 설계서 |
| F3-PC-05 | 양보 조건 분리 | `flexible`과 `inflexible`을 구분해 출력한다. 근거가 없는 항목에는 「추정」 표식을 붙인다 | 필수 | 설계서 |
| F3-PC-06 | 접촉 가능 상태 | `contactability`는 최종 접촉 후 경과와 응답 이력을 근거로 판정한다. 「통화 어려움, 문자 선호」와 같은 로그 표현을 note에 남긴다 | 필수 | 설계서 |
| F3-PC-07 | 카드 표시 | 카드를 화면에 표시할 때 항목별 근거를 펼쳐 볼 수 있어야 한다. 근거는 클릭하면 해당 상담 로그로 이동한다 | 필수 | 신규 |
| F3-PC-08 | 카드 정정 | 중개사가 카드의 각 항목을 직접 정정할 수 있다. 정정 내용은 상담 로그에 기록되어 다음 판정의 입력이 된다 (F3-TR-02) | 필수 | 설계서 |
| F3-PC-09 | 카드 이력 | 같은 대상의 이전 카드와 현재 카드를 비교할 수 있다. 입장이 언제 바뀌었는지가 중개사에게 정보다 | 권장 | 신규 |

### 11. 배치 판정 — 캠페인

문자 발송은 판단 대상이 아니라 도구다. 우선순위 큐에 넣지 않는다.

```text
[1] 대상 선정 — SQL                                 LLM 0회
    "헬리오 33평 임대인 중 6개월 미접촉"           →  104명
[2] 대리 배치 실행 — 얕은 판정                       LLM 104회 (병렬, 캐시 히트 제외)
    매도 의향 표명한 적 있음        8명   → 지금이 적기
    만기 임박, 결정 앞둠           23명   → 계획 확인
    최근 명시적 거절               11명   → 발송 제외
    임차인이라 결정권 없음          6명   → 발송 제외
    접촉 이력 부족, 판단 불가       56명   → 일반 시세표
[3] 세그먼트별 문안                                  LLM 4회
[4] 미리보기 → 일괄 승인 → 발송
[5] 전원 상담 로그 자동 append → 재연락 주기 갱신
```

> **[참고]** **캠페인의 실제 가치는 17명을 빼는 것이다.** 최근 거절한 11명과 결정권 없는 6명은 로그를 읽어야 알 수 있다. 거절한 사람에게 또 보내면 관계가 상한다. 조건 세그먼트만으로는 이 판단이 불가능하다.

### 18. 수용 기준

| # | 기준 | 검증 방법 |
|---|---|---|
| 1 | 후보 추출과 대상 선정이 LLM 없이 동작한다 | 유닛 테스트 |
| 2 | 포지션 카드의 각 판정 항목에 근거 원문이 있거나 「추정」으로 표시된다 | 표본 20건 검수 |
| 3 | 매물 대리와 손님 대리가 서로의 로그를 읽지 않는다 | 실행 로그 확인 |
| 4 | 양측 대리 방식이 단일 프롬프트 대비 우수하다 | 케이스 20건 비교 (19장) |
| 5 | 중개 판정이 앵커 1 + 후보 N을 한 번의 호출로 받으며 순위와 상호 비교 근거를 낸다 | 호출 로그 · 출력 확인 |
| 6 | 중개 판정이 후보 중 일부를 기각하며 사유가 로그에 남는다 | 실행 로그 확인 |
| 7 | 후보 추출 조건에 대리의 추정값이 반영된다 | 장부 표기값과 다른 케이스 재현 |
| 8 | 손님 또는 매물을 저장하면 5초 이내 같은 화면에 판정 결과가 표시된다 | 성능 측정 |
| 9 | 교차 판정 결과에 컷이 없다 (세대 상세의 기각 미노출은 예외이며 판정 수는 줄지 않는다) | 판정 수 = 노출 수 + 기각 수 대조 |
| 10 | 가격 변경 저장 시 새로 조건에 맞게 된 상대가 결과에 포함된다 | 27.5억 → 26.5억 시나리오 |
| 11 | 대상 100명 캠페인에서 발송 제외 대상이 로그 근거와 함께 식별된다 | 캠페인 시연 |
| 12 | 대상 100명 캠페인의 문안 생성 LLM 호출이 10회 이하다 | 호출 계측 |
| 13 | 포지션 카드가 캐시되어 로그 변경이 없으면 재생성되지 않는다 | 캐시 히트율 계측 |
| 14 | 중개사가 정정한 포지션이 다음 판정에 반영된다 | 정정 → 재판정 시나리오 |
| 15 | F3를 중단해도 F1의 모든 기능이 동작한다 | 장애 주입 테스트 |

#### 18.1 멀티 에이전트 구조 검증

> **[참고]** **"왜 나눴냐"에 수치로 답한다.** 같은 케이스 20건에 대해 ① 단일 프롬프트 ② 양측 대리 후 중개 판정 두 방식을 돌려 비교한다. 비교 지표는 — 걸림돌을 구체적으로 특정했는가 · 양보 지점을 제시했는가 · 로그의 비구조화 근거를 인용했는가 · 중개사 블라인드 선호도. 심사에서 답이 의견이 아니라 수치가 된다.

> **[주의]** **배치 판정은 멀티 에이전트가 아니다.** 대리 하나를 N번 돌리는 것이며, 교차 옵션(11.4)을 켜야 중개 판정이 개입한다. 유용하지만 멀티 에이전트 논증에는 기여하지 않는다 — 발표에서 이 점을 감추지 않는다.
