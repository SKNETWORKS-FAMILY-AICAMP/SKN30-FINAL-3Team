# GPU 상시 운영에서 조건부 자동 교차 판정 검토

출처: [후속 사용자 검토 요청](../../requirements/sources/f3-worker-auto-judgment-review-2026-09-09.md).

사용자가 제공한 “현 상황에서는 GPU를 상시 띄운다”를 설계 전제로 사용한다.
앞선 수동 요청 우선 권고를 **조건부 자동 선행 계산 + 저장 결과 목록 + 필요 시 수동 갱신**으로 수정한다.
자동 실행 정책·임계값은 제안이며 승인된 [ADR-0018](../../../.agents/skills/project-wiki/references/decisions/ADR-0018-f3-save-trigger-anchor-card-scope.md)은 아직 바꾸지 않았다.

## 비용 판단 수정

고정 사양·고정 GPU 대수·동일 기동 시간의 전용 GPU라면 호출을 늘려도 GPU 임대료는 대체로 같다.
추가 호출마다 비용이 드는 OpenAI/Bedrock과 구분해야 한다. 이 전제에서 “총비용 증가”만으로 자동 판정을 배제한 이전 권고는 적절하지 않다.
빈 GPU 용량으로 사전 계산해 사용자 대기를 줄일 이익이 있다. 사용자 대기도 제품 비용이다.
Pod의 실행 시간 중심 과금 근거: [RunPod 가격 문서](https://docs.runpod.io/pods/pricing). 현재 요금이나 실제 청구액을 조사한 것은 아니다.

남는 제약은 GPU **처리 용량·응답 지연·최신성**이다. backlog 때문에 챗봇/수동 재조회가 느려지거나
용량 증설·기동 시간 연장·유료 API fallback이 필요하면 그때 증분 비용이 생긴다.
자동 fallback은 제안하지 않는다. local의 개인 과금 API에서는 자동 사전 계산을 명시적으로 선택하거나 fake로 검증한다.
F2/general은 분리 GPU가 기본이므로 주된 추론 경합은 F3와 general을 사용하는 챗봇 사이이며, F2는 앱 CPU·RDS 같은 공통 자원에서 영향을 받을 수 있다.

## 두 단계 조건 판정

“실행할 조건”은 AI 결과를 미리 알아야 하는 조건과 코드로 알 수 있는 조건을 구분한다.

| 단계 | 실행 조건·생략 조건 | 모델 호출 |
|---|---|---|
| 1. 값싼 접수 gate | 저장 완료·허용 사무소·삭제되지 않은 유효 대상·활성 업무 상태·지원 거래 유형. 관련 입력의 실질 변경 또는 미생성 결과가 있어야 함 | 없음 |
| 2. 중복·최신성 | 동일 입력 진행 작업이 있으면 합침. 유효 완료 결과면 재사용. 연속 저장은 짧은 configurable 지연 동안 최신 revision으로 병합 | 없음 |
| 3. 앵커 카드 확보 | 입력·상담·설정·날짜 identity가 같은 카드면 재사용, 아니면 생성. 허용된 입력이 부족하면 정보 부족 상태 | hit 0, miss 필요 |
| 4. 후보 SQL | 현재 후보 선정 로직과 동일한 카드의 추정 조건으로 결정적 후보 검색. 후보 0건이면 “후보 없음” 저장 | 없음 |
| 5. 최종 입력 비교 | 필요한 후보 카드 확보 후 이전 판정 identity와 대조. 같으면 결과 재사용, 다르면 판정 실행 | 후보 miss 및 필요한 최종 판정만 |

현재 활성 상태 상수(`RECEIVED`/`ACTIVE`), top-5, 가격 허용폭은 기존 구현값이며 새 정책의 승인된 수치가 아니다.
원장 가격만 좁게 필터링해 카드 생성 전 탈락시키면 **카드 추정가로 연결될 후보를 놓칠 수 있다.**
사전 SQL gate를 추가한다면 기존 후보선정의 상위집합임이 검증된 넓은 필터만 사용한다. 안전하게 입증되지 않으면 4단계까지 판단을 미룬다.
상담이 없다는 이유만으로 무조건 제외하거나, AI가 강함으로 판정할 때만 AI를 실행한다는 순환 조건을 두지 않는다.

## 이벤트별 자동 처리 범위

| 사건 | 후속 처리 |
|---|---|
| 신규·가격/조건·상담 등 의미 있는 변경 | 해당 앵커를 gate에 넣고 최신 카드→후보→판정을 자동 진행 |
| 메모·담당자 등 비입력 수정·같은 값 재저장 | 판정 생략. 담당자 표시·목록 필터 같은 읽기 데이터만 반영 |
| 새 상대가 기존 검색 조건에 진입 | 영향받는 반대편 앵커도 dirty 처리. 변경한 행 하나만 계산하고 끝내지 않음 |
| 삭제·종료·권한 변경 | 노출 차단/이전 결과 stale, 관련 앵커 후보 집합 재평가. 삭제된 카드 모델 생성은 생략 |
| 모델/시간 기준 변경 | 유효 대상에 대해 점진적 재검증·재계산. 일괄 동시 호출하지 않음 |
| 기존 데이터 | 최초 backfill을 낮은 우선순위로 나눠 접수하고 이후 이벤트를 따라감 |

1차 대상은 gate를 통과한 활성 장부다. “이전에 사용자가 열어본 대상만”으로 제한하지 않아 새로운 기회를 발견하게 한다.
이미 판정한 후보의 역참조만으로 영향 대상을 찾으면 새 후보 유입을 놓친다. 거래유형·단지 등 넓은 영향 범위와 새 후보 진입 검사를 함께 사용한다.
작은 dev에서는 사무소·거래유형별 영향 앵커를 먼저 넓게 dirty 처리한 뒤 **SQL/입력 identity로 실제 재판정 대상을 줄이는** 방식이 가능하다.
데이터 증가 시 의존성 인덱스와 조건별 버전으로 좁힌다. raw 이벤트 수만큼 전수 LLM 호출하지 않는다.
후보 순위는 앵커 방향과 전체 후보 집합에 종속되므로 반대 방향 결과를 뒤집어 재사용하지 않는다.

## 큐·공정성과 서버 확장

- 사용자 갱신/보고 있는 결과 → 조건부 자동 판정 → backfill 순으로 우선순위를 둔다. 오래 기다린 자동 작업은 승격한다.
- `due_at`·`next_attempt_at`·priority·desired_revision을 DB에 저장한다. 메모리 타이머는 작업·병합의 정본이 아니다.
- 판정 전체를 한 Worker가 오래 점유하는 현재 흐름에서는 단계 사이 양보/재선점 또는 역할별 큐를 추가한다. 단순 정렬 변경만으로 실행 중인 긴 작업을 선점할 수 없다.
- general 모델의 최대 동시 호출 예산을 공유한다. Worker 2대를 만들었다고 후보 호출 예산을 무조건 5→10으로 늘리지 않는다.
- API/Worker 분리 여부와 관계없이 GPU가 포화되면 Worker 증설만으로 빨라지지 않는다. [서버 분리 보완](worker-deployment-review.md)을 함께 적용한다.
- 장애 뒤에는 이벤트를 복원하고 같은 대상의 오래된 대기 revision을 합쳐 최신 건만 계산한다. 현재성 검증 없이 과거 결과를 최신으로 내보내지 않는다.
- 날짜로 변하는 카드/후보 점수는 현재 UTC bucket 경계에 점진적 dirty 처리를 하되, 활동량과 변경 의미에 맞춘 후속 freshness 정책을 별도로 합의한다.

## 기존 설계에서 추가되는 것

기존 Worker·AI facade·카드/판정 테이블을 재사용한다. outbox·입력 revision·완료 identity는 [이벤트 설계](position-card-events.md)를 따른다.
추가되는 책임은 eligibility, 영향 앵커 계산, durable 병합·우선순위, 자동 실행 범위와 최신 결과 읽기 모델이다.
`trigger_type`을 무조건 USER_REQUEST로 바꿔 우회하지 않고 `AUTO_ELIGIBLE` 같은 명시적 실행 이유와 `CARD_ONLY`/`FULL_JUDGMENT` 실행 범위를 분리하는 안을 권고한다.
카드 API를 먼저 독립 제품으로 완성할 필요는 없다. 카드 생성/재사용은 결과 목록을 위한 내부 단계로 유지하고 카드는 근거 상세에서 제공한다.
일반 이벤트 소비와 AI 실행을 분리하더라도 별도 AWS 서비스가 필수는 아니다. 작은 DB consumer와 기존 Worker를 현재 EC2에 두고 측정 후 CPU Worker 서버를 분리할 수 있다.

## 사용자 가치와 검증

대표 동선은 “저장 → 다른 업무 → 교차 판정 목록에서 준비된 결과 확인”이다. 결과가 완성되기 전에 즉시 열면 남은 대기는 여전히 발생한다.
이를 숨기지 않고 이전 결과·갱신 중을 구분한다. 카드만 선생성하는 것보다 최종 판정까지 선행 계산해야 후보 카드·최종 비교 대기를 줄인다.

| 판단 지표 | 비교 방법 |
|---|---|
| 준비된 결과 조회 비율 | 첫 조회 때 CURRENT 결과가 존재한 대상 비율: 수동 방식 vs 조건부 자동 방식 |
| 실제 사용자 대기 | 결과 화면 진입→사용 가능한 최신 판정까지 p50/p95, 수동 클릭 수 |
| 반영 지연 | 의미 있는 저장→최신 결과 완료 p50/p95, 가장 오래된 dirty 작업 나이 |
| 공유 모델 영향 | 자동 작업을 켠/끈 상태의 챗봇/사용자 갱신 p95, GPU queue와 처리량 |
| 불필요한 계산 | 변경 병합률·완료 재사용률·조회되지 않은 결과 비율·중복 호출 수 |
| 정확성 | 새 상대 진입·후보 없음→있음·삭제·연속 수정에서 오래된 CURRENT·누락 0건 |

표본과 시간 목표는 합의 전이다. GPU 시간 비용이 같은 조건에서 사용자 대기 감소가 충분하고 interactive 지연이 허용 범위면 자동 선행 계산의 실효성이 있다.
검토용 사용성 과제는 [결과 목록 요구안](../../requirements/f3/judgment-results-list.md)에 둔다.
