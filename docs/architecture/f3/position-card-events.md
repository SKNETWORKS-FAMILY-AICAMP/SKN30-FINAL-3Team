# F3 이벤트 처리와 완료 결과 재사용 설계안

[현황·문제](position-card-review.md)와 [결과 목록 요구안](../../requirements/f3/judgment-results-list.md)을 위한 공통 저장·재사용 제안이다.
후속 GPU 상시 운영 조건에 따른 실행 정책은 [조건부 자동 판정](conditional-auto-judgment.md)이 정본이며, 독립 카드 API는 보조 대안이다.
AI는 프롬프트·모델 호출을, Backend는 이벤트 소비·권한·DB·트랜잭션을 소유하는 기존 경계를 유지한다.

## 권고 흐름

1. F1 저장 transaction에서 장부 변경과 최소 변경 이벤트를 함께 기록한다.
2. 별도 소비자가 이벤트를 선점하고 조건·중복·변경 병합을 거쳐 최신 입력 작업을 접수한다. API는 AI나 소비자를 기다리지 않는다.
3. 카드 생성 facade·후보 SQL로 실행 필요성을 확인하고 필요한 교차 판정까지 자동 진행해 DB에 저장한다.
4. 결과 목록·상세 GET은 저장된 판정·최신성·갱신 상태를 반환한다. 카드는 양측 근거 상세에서 제공한다.
5. 사용자 갱신 요청도 유효 완료 결과/진행 작업을 재사용하며, 새 작업이면 우선 처리한다.

이벤트 전달만 추가해도 모델 호출 횟수 자체가 줄지는 않는다. 변경 병합·카드 재사용·완료 판정 재사용을 함께 적용해야 한다.
자동 판정은 의미 있는 변경·유효 대상·후보 존재 조건을 만족한 경우로 제한한다. ADR-0018의 후속 변경을 제안하는 상태이며 아직 승인·구현된 정책은 아니다.

## 저장 이벤트와 누락 방지

`f3_input_changed:v1`이라는 이름의 최소 이벤트를 제안한다. 봉투는 기존 [이벤트 계약 규칙](../../../.agents/skills/project-wiki/references/contracts/events.md)을 따른다.
내용은 `event_id`, `brokerage_id`, 원천 종류·ID·revision, 변경 필드 이름, 시각·trace_id다.
상담 본문·이름·연락처·모델 응답은 넣지 않는다. ID도 내부 접근·보존 통제 대상이다.
세대·단지처럼 영향 대상이 여럿이면 원천 참조만 쓰고, 소비자가 대상별 카드 작업으로 펼친다.

F1과 이벤트 기록의 원자성이 필요하므로 **transactional outbox**를 제안한다.
소비자의 작업 접수와 이벤트 완료 표기도 같은 DB transaction에서 수행한다.
AI가 실패해도 이벤트 완료와 구분하여 카드 작업이 독립 재시도한다. 장부 commit 후 프로세스가 죽어도 미처리 이벤트가 남는다.
중복 event_id, 동일 대상·입력 작업의 unique 제약, `FOR UPDATE SKIP LOCKED`, lease와 attempt fencing을 둔다.

**기존 실패 의미와의 차이:** outbox INSERT 자체가 실패하면 같은 transaction의 F1 저장도 실패한다.
Worker·모델 장애는 F1에 영향을 주지 않지만, 이는 현재 “F1 commit 후 F3 접수 실패는 무시”와 다르다.
이벤트 내구성을 저장 성공의 일부로 보는 안이며 구현 전에 계약 합의가 필요하다.
F3 관련 기록 오류에도 F1 성공을 반드시 유지해야 한다면, 짧은 접수 timeout과 durable 원장 revision을 스캔하는 보정 작업을 대안으로 설계한다.
commit 후 메모리 BackgroundTasks만 사용하는 방식은 중단 시 누락을 해소하지 못한다.
이중 쓰기 문제와 outbox의 근거: [AWS 패턴 문서](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

## 최신성·무효화 범위

| 변경 원천 | 필요한 반영 |
|---|---|
| 매물/구입장 가격·조건·상태 | 해당 카드 revision 및 반대편 후보 검색 범위의 revision 변경 |
| 상담 추가·수정·삭제, 접촉 이력 | 허용 상담 범위에 속한 모든 대상 카드 무효화. 장부 row_version만으로 대체하지 않음 |
| 세대·단지·당사자 관계·공동중개 정보 | 실제 모델 snapshot과 후보 SQL에서 사용하는 의존 대상에 반영 |
| 대상/부모 세대 삭제·접근 권한 변경 | 조회 차단과 진행 작업 저장 차단. 이전 카드 보이기 정책보다 우선 |
| 카드·판정 모델/설정/prompt/workflow 변경 | 각 capability의 구성 fingerprint 변경. ID가 같아도 설정 내용이 바뀌면 감지 |
| 날짜 경계 | 현재 카드 지문의 UTC 일자 기준을 그대로 적용. KST 전환은 별도 계약 변경 |
| 새 상대 후보·기존 후보 삭제·조건 진입 | 과거 top-5에 없던 상대도 판정 결과를 stale로 만듦. 후보 0건 결과도 동일 |

이벤트 소비는 늦을 수 있으므로 `invalidated_at` 또는 소비 완료 여부만으로 최신이라고 답하면 안 된다.
1차에는 관련 원천 변경 transaction에서 증가시키는 사무소별 입력 revision과 활성 구성·UTC bucket을 조회한다.
revision과 산출물의 기록값이 다르면 보수적으로 STALE을 반환한다. 소비자가 의존성을 검증하면 동일 산출물을 새 revision에서 확인한 것으로 갱신할 수 있다.
사무소 단위 revision은 구현이 단순하지만 관련 없는 변경까지 stale로 만들고 쓰기 경합을 늘릴 수 있다.
대상별 revision·의존성 인덱스로 좁히는 최적화는 측정 후 한다. 원천 누락 없이 전체 쓰기 경로를 포함하는 것이 선행 조건이다.

## 카드 작업과 저장 모델

기존 `negotiation_position_analysis/price/evidence`를 재사용하고 본문을 새 테이블에 복제하지 않는다.
추가 후보는 `match_change_outbox`, 입력 revision, 대상별 현재 카드·생성 job 참조 및 최신성 메타데이터다.
작업 실행은 기존 `agent_run` 기반을 활용하되 `run_type`/명시적 실행 범위로 **카드만 실행**과 **판정 실행**을 구분한다.
현재 `trigger_type`은 저장 출처이면서 실행 범위이므로 독립 카드 요청을 일반 USER_REQUEST로 넣으면 판정까지 진행할 위험이 있다.
기존 주차 실행의 handoff 호환성을 유지하고 명시적 실행 범위로 옮긴다. 자동 판정 경로에는 FULL_JUDGMENT 범위를, 카드만 보는 보조 경로에는 CARD_ONLY 범위를 제안한다.

- 미착수 동일 대상 변경은 최신 revision으로 합친다. 실행 중 호출은 강제 취소를 보장하지 않고 늦은 결과를 현재 카드로 승격하지 않는다.
- 카드 입력 fingerprint별 생성 선점을 두어 서로 다른 판정 실행의 동일 후보 miss를 합친다. 모델 대기 중 DB lock을 유지하지 않는다.
- 후보 병렬 생성의 성공 결과는 다른 후보 실패와 무관하게 개별 검증·저장한다. 전체 판정은 모든 필수 카드가 준비된 뒤에만 진행한다.
- 저장 시 lease·attempt·현재 입력 revision을 비교하고 현재 카드 포인터를 조건부 갱신한다. 검증과 포인터 갱신 사이 원천 변경도 같은 잠금/원자적 비교 규칙으로 차단한다.
- 프로세스가 모델 응답 수신 후 DB 저장 전에 죽으면 외부 호출은 반복될 수 있다. DB 멱등성은 모델 비용의 exactly-once 보장을 뜻하지 않는다.

## 완료 교차 판정 재사용

앵커 ID·row_version만으로 캐시하지 않는다. 판정 생성 시 다음 identity를 기록한다.

`사무소 + 앵커 방향/입력/카드 + 전체 SQL 후보 snapshot fingerprint + 상위 카드 집합/입력 + 후보선정 버전/정책 + 카드·판정 AI 구성 + 날짜 bucket`

유효성 확인은 먼저 가벼운 revision·구성·날짜를 비교한다. 같으면 저장 결과를 반환할 수 있다.
다르면 Worker가 최신 앵커 카드·후보 SQL·후보 카드 identity를 확인한다. 동일한 판정 입력이면 AI를 다시 부르지 않고 기존 결과를 연결한다.
새 후보 진입 등으로 identity가 다르면 재판정한다. 앵커 방향이 다른 판정과 후보별 일부 순위는 재사용하지 않는다.
입력 읽기 전후 revision이 달라졌거나 저장 직전 변경되면 CURRENT로 승격하지 않고 최신 작업으로 전환한다.

DB에는 identity별 완료 결과 참조와 현재 대상의 결과 포인터를 둔다. 기존 `match_evaluation`과 후보 판정·근거를 재사용한다.
기존 행에는 전체 identity가 없으므로 단순 역산으로 CURRENT를 부여하지 않는다. 최초 검증/재생성 전에는 과거 결과로 취급한다.
새 GET 조회 계약은 과거 snapshot과 최신 결과를 구분하고, POST는 완료 재사용 200·작업 접수/재사용 202를 구분하는 안이다.
현재 POST가 항상 202인 계약·Frontend decoder는 후속 구현에서 함께 변경한다.

## 자동 사전 계산의 대안

| 정책 | 효과·비용 | 제안 |
|---|---|---|
| 조건부 자동 판정 + 완료 재사용 | 상시 GPU의 여유 용량으로 준비된 결과 제공. 변경 병합·후보 gate·우선순위 필요 | 후속 요청 반영 1차 권고 |
| 사용자 요청 + 유효 완료 결과 재사용 | 최초/변경 후 사용자 대기가 남음. local 과금 API에서 선택 가능 | 수동 대안 |
| 이전에 판정을 요청한 대상만 자동 재계산 | 대상 감소, 새 기회 발견 범위도 감소 | backlog가 감당되지 않을 때 선택 |
| 조건 없는 모든 저장 판정 | 비입력 수정·동일 입력까지 처리량 낭비 | 권고하지 않음 |

보존·삭제 정책, 사전 계산 범위와 처리 SLA는 [OQ-F3-01~03](../../../.agents/skills/project-wiki/references/open-questions.md)을 따른다.
