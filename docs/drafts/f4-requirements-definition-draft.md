## 1. 개요

### 1.1 목적

F4는 중개사가 하루를 시작하고 반복 업무를 처리하는 데 쓰는 보조 기능을 모은다. F1이 저장한
장부와 상담 기록을 재료로 쓰되, F3처럼 양측 입장을 판단하지 않고 **이미 정해진 사실을 제때
꺼내 놓거나 사용자가 고칠 초안을 만든다.**

F3와 갈리는 지점이 여기다. F3는 조건표에 안 들어간 말을 읽어 거래 가능성을 판단한다. F4는
판단하지 않는다. 만기일은 장부에 적힌 날짜이고, 재연락 시점은 마지막 접촉에서 세는 값이며,
문자 초안은 이미 나온 결과를 문장으로 옮기는 일이다.

### 1.2 범위

| 구분 | 내용 |
|---|---|
| 포함 | 일정·할 일 브리핑(Time Keeper) · 캘린더 |
| 보류 | 뉴스 요약 · 문자 발송 초안 · 블로그 광고글 초안 · 챗봇 |
| 제외 | 실발송 · 계약 판단 · 가격 평가 · 법률 판단 · 양측 포지션 판단(F3 소유) |
| 타 기능 경계 | 저장·조회·화면은 F1, 음성 인식은 F2, 양측 판단은 F3 |

### 1.3 구성 서비스와 진행 상태

| 서비스 | 내용 | 상태 | 본 문서 절 |
|---|---|---|---|
| Time Keeper | 장부의 날짜에서 일정·할 일을 모아 아침에 알린다 | **구현됨** | [3장](#3-time-keeper--일정할-일-구현됨) |
| 캘린더 | Time Keeper 일정을 달력 형태로 보여주고, 추후 F2 연동으로 자동 일정 추가를 검토한다 | 구현 예정 (코드 미착수) | [4장](#4-캘린더-구현-예정) |
| 뉴스 요약 | 날짜 기준으로 부동산 뉴스를 찾아 요약한다 | 보류 | [5.1](#51-뉴스-요약-보류) |
| 문자 발송 초안 | 만기 안내·매물 등록 알림 등 문자 초안을 만든다 | 보류 | [5.2](#52-문자-발송-초안-보류) |
| 블로그 광고글 초안 | 사용자 글의 어투를 반영한 광고글 초안을 만든다 | 보류 | [5.3](#53-블로그-광고글-초안-보류) |
| 챗봇 | 대화형 인터페이스로 F1~F4 화면을 오가지 않고 물을 수 있게 한다 | 보류 (범위 후보 1번만 로컬 프로토타입) | [5.4](#54-챗봇-제안--설계-전) |

보류된 서비스는 대상 데이터와 외부 연동이 확정되지 않았다. 상세 요구사항은 각 서비스를
실제로 설계할 때 이 폴더에 파일을 추가한다. 빈 파일을 미리 만들지 않는다.

## 2. 공통 요구사항 (F4-CM)

전 서비스에 공통으로 적용되는 원칙이다. 보류·제안 서비스를 실제로 설계할 때도 아래 원칙을
벗어나지 않는다.

| ID | 요구사항 | 상세 | 등급 |
|---|---|---|---|
| F4-CM-01 | 판단하지 않는다 | F4는 장부에 있는 사실과 이미 나온 결과를 재료로 쓴다. 양측 포지션 판단과 거래 가능성 판정은 F3가 소유한다 | 필수 |
| F4-CM-02 | 날짜 계산은 코드가 한다 | 만기·기한·경과일 계산에 모델을 쓰지 않는다 | 필수 |
| F4-CM-03 | 없는 데이터를 만들지 않는다 | 장부에 대응 컬럼이 없는 항목은 화면에 종류 자체를 만들지 않는다. 빈 값을 0건으로 채워 있는 것처럼 보이게 하지 않는다 | 필수 |
| F4-CM-04 | 승인 전 확정 금지 | F4가 만든 초안과 제안은 사용자가 확인하고 승인해야 F1 데이터가 되거나 외부로 나간다 | 필수 |
| F4-CM-05 | F4 없이 F1 동작 | F4가 응답하지 않아도 F1의 모든 기능이 정상 동작한다. F4 영역만 실패 상태를 표시하고 재시도를 제공한다 | 필수 |
| F4-CM-06 | 쓰기 범위 | F4는 F1의 장부 필드를 직접 고치지 않는다. 현재 구현된 Time Keeper는 조회만 한다 | 필수 |
| F4-CM-07 | 언어 | 화면 문구와 생성 문안은 한국어로 만들고 현업 표기를 그대로 쓴다 | 필수 |
| F4-CM-08 | 기준 시각 | 업무일의 경계는 **KST(한국 표준시) 오전 09:00**으로 정한다. 자정이 아닌 이 시각을 하루의 시작으로 삼아 만기·기한·경과일을 계산하며, `F4-TK-18` 아침 브리핑도 같은 09:00 KST 기준으로 그날 첫 접속 여부를 판단한다. UTC를 그대로 쓰면 이 경계가 9시간 밀린다 | 필수 |

> **F4-CM-08 확정:** 시간대(KST)와 업무 시작 시각(09:00)을 하나로 합쳐 **"업무일 경계 =
> 09:00 KST"**로 확정했다(사용자 확인, 2026-09-04). 날짜·기한 계산과 아침 브리핑 판단이 모두
> 이 경계를 기준으로 삼는다.

### 2.1 F1 알림 요구사항과의 관계

F1은 이미 알림 요구사항을 갖고 있다. F4는 그것을 대체하지 않고 F4 쪽 구현으로 채운다.

| F1 요구사항 | F4에서 채우는 방식 | 상태 |
|---|---|---|
| F1-AL-01 만기 도래 알림 | F4-TK-02가 임대차 만기를 일정 목록에 싣는다 | 구현됨 |
| F1-AL-03 미접촉 알림 | F4-TK-04가 재연락 기한을 만들고 방치 기간순으로 세운다 | 구현됨 |
| F1-AL-04 알림 센터 | F4-TK-08 상단바 알림 버튼이 목록을 연다 | 구현됨 |
| F1-AL-05 알림 규칙 설정 | 기준값은 코드 상수. 사무소별 설정 여부 미확정 (OQ-011) | 미구현 |
| F1-AL-02 일정 임박 알림 | 일정 테이블(F1-SC) 자체가 없다 | 미구현 |
| F1-AL-06 담당자 귀속 | 응답에 `assigned_user_id`는 싣지만 담당자별 필터는 없다 | 미구현 |

## 3. Time Keeper — 일정·할 일 (구현됨)

장부에 이미 있는 날짜에서 "언제까지 무엇을 해야 하는가"를 모아 하루 시작에 한 번 보여준다.
**조회 전용**이며 장부를 바꾸지 않고 모델을 호출하지 않는다.

「만기도래일 보기」가 현행 장부에서 쓰이지 않은 이유는 사용자가 열어야만 보이기 때문이다.
그래서 별도 화면이 아니라 접속하면 스스로 찾아오는 창으로 둔다.

### 3.1 대상 일정

일정 한 건은 종류를 갖는다(F4-TK-01). 종류는 고정 열거형이 아니며 대응 데이터가 생기면 늘어난다.
클라이언트는 모르는 종류를 오류로 다루지 않고 코드를 그대로 표시한다.

| ID | 요구사항 | 상세 | 등급 |
|---|---|---|---|
| F4-TK-02 | 임대차 만기 | 세대의 현 임대차 만기와 손님이 지금 사는 집의 임대차 만기를 싣는다 | 필수 |
| F4-TK-03 | 구입 의뢰 만기·희망 입주일 | 구입 의뢰 자체의 만기와 손님의 희망 입주일을 싣는다 | 필수 |
| F4-TK-04 | 재연락 기한 | 마지막 접촉 시각 + 재연락 주기. 세대·손님 양쪽 적용. **기한이 아무리 지나도 목록에서 빼지 않는다** | 필수 |
| F4-TK-05 | 매물 조건 재확인 기한 | 매물 접수일 + 재확인 주기. 재연락과 동일하게 지난 기한을 빼지 않는다 | 권장 |
| F4-TK-06 | 종료된 대상 제외 | 종료된 구입 의뢰·내려간 매물은 알리지 않는다 | 필수 |

**아직 담지 못하는 항목** (대응 데이터 없음 → F4-CM-03에 따라 종류 자체를 만들지 않음):
계약 체결일 / 계약금·중도금·잔금 지급일 / 신고·서류 제출 기한 / 임장·매물 방문일 / 명도일.
해당 테이블(F1-CT, F1-SC 등)이 생기면 어휘에 종류를 더한다. (4장 캘린더의 F2 자동 추가 제안이
실현되면 이 테이블 공백이 먼저 해소돼야 한다.)

### 3.2 조회 범위와 정렬

| ID | 요구사항 | 상세 | 등급 |
|---|---|---|---|
| F4-TK-07 | 앞뒤 창 | 앞으로 볼 기간 + 이미 지난 기한을 되돌아볼 기간. 되돌아보는 기간은 **날짜가 적힌 종류에만** 적용, 재연락·재확인은 아래쪽 경계 없음 | 필수 |
| F4-TK-09 | 기한 순 정렬 | 기한 이른 순, 동일 날짜는 종류·식별자로 안정화 정렬 | 필수 |
| F4-TK-10 | 종류별 상한 | 종류마다 앞에서 몇 건씩만 싣는다 | 필수 |
| F4-TK-11 | 잘린 건수 표시 | 상한에 걸려 빠진 건수를 종류별 총계와의 차이로 표시 | 필수 |
| F4-TK-12 | 해당 종류만 표시 | 건수 0인 종류는 화면에 나오지 않는다 | 필수 |

기준값은 코드 상수이며 승인된 수치가 아니다 (사무소별 설정 여부는 OQ-011 미해결).

| 기준 | 현재 기본값 |
|---|---|
| 앞으로 보는 기간 | 90일 |
| 되돌아보는 기간 | 7일 |
| 재연락 주기 | 30일 |
| 매물 재확인 주기 | 30일 |
| 종류별 상한 | 3건 |

### 3.3 표시와 연락

| ID | 요구사항 | 상세 | 등급 |
|---|---|---|---|
| F4-TK-13 | 대상 표기 | 세대는 단지·동·호, 구입장은 손님 이름으로 표기 | 필수 |
| F4-TK-14 | 남은 기간 표시 | D-day 표시, 오늘·경과 건은 색이 아닌 문구로 구분 | 필수 |
| F4-TK-15 | 기준일 고정 | 남은 일수는 서버 계산값을 그대로 쓰고 화면이 재계산하지 않음 | 필수 |
| F4-TK-16 | 연락 대상 동반 | 행마다 연락할 인물·연락처를 함께 싣는다 | 필수 |

### 3.4 브리핑과 진입

| ID | 요구사항 | 상세 | 등급 |
|---|---|---|---|
| F4-TK-08 | 알림 버튼 진입 | 상단바 알림 버튼이 목록을 연다. 열 때마다 다시 읽음 | 필수 |
| F4-TK-18 | 아침 브리핑 | 업무 시작 시각(09:00 KST, `F4-CM-08`) 이후 그날 첫 접속 시 목록이 자동으로 한 번 열림 | 필수 |
| F4-TK-19 | 하루 한 번 | 같은 업무일에는 다시 자동으로 열리지 않음. 알림 버튼으로는 언제든 재진입 | 필수 |
| F4-TK-20 | 빈 날 메시지 표시 **(구현 예정 — 코드 미반영)** | 알릴 것이 없는 날에도 브리핑 창은 그대로 열리고 **"일정이 없습니다."** 문구를 표시한다. 창을 아예 띄우지 않던 기존 구현에서 바뀌는 부분이며, 아직 코드에는 반영되지 않았다 | 필수 |
| F4-TK-21 | 미확인 건수 표시 | 알림 버튼에 창 안의 건수 표시 | 권장 |

> **설계 원칙:** 브리핑 판단은 **브라우저**가 한다. 서버 정기 실행을 두지 않는다는 F3 설계
> 원칙을 따른 것으로, 앱이 열려 있어야 뜨고 문자·이메일·푸시 알림은 없다. 브라우저마다
> 따로 기록하므로 PC·계정별로 각각 한 번씩 뜬다.

> **F4-TK-20 변경 참고:** 기존 안은 "빈 창이 매일 뜨면 아무도 읽지 않는다"는 이유로 빈 날엔
> 아예 창을 띄우지 않았다. 이번 요청으로 "빈 날에도 열리되 빈 상태임을 명시"하는 쪽으로
> 스펙을 바꿨다. `F4-TK-19`(하루 한 번)는 그대로 유지되므로, 같은 업무일 안에서 반복해
> 자동으로 뜨지는 않는다. **이 변경은 스펙 확정일 뿐 아직 프론트엔드 코드에는 반영되지
> 않았다 — 코드 작업은 별도 요청 시 시작한다.**

## 4. 캘린더 (구현 예정)

**코드 작업 미착수.** 이번 요청으로 새로 제안된 서비스다. **아직 설계도 구현도 하지 않았고,
아래는 사용자가 제시한 방향일 뿐 확정된 요구사항이 아니다.** Time Keeper가 이미 모으는 일정
데이터를 달력 형태로도 보여주는 것을 기본으로 하고, 추후 F2 연동을 통한 자동 일정 추가를 함께
검토한다. 이 장 전체는 스펙 초안이며, 실제 프론트엔드·백엔드 구현은 이 문서와 별개로 요청이
있을 때 시작한다.

### 4.1 기본 기능 — 할 일 달력

| ID | 요구사항 | 상세 | 등급 | 상태 |
|---|---|---|---|---|
| F4-CAL-01 | 월/주 달력 뷰 | Time Keeper가 다루는 일정 종류(`F4-TK-01`)를 달력 형태로 표시한다. 날짜 칸에 해당일 일정을 얹는다 | 제안 | 설계 전 |
| F4-CAL-02 | 목록 뷰와 데이터 공유 | 달력 뷰와 Time Keeper 목록 뷰는 같은 일정 데이터를 다른 형태로 보여준다. 데이터 정의를 이중화하지 않는다 | 제안 | 설계 전 |

Time Keeper와 같은 공통 원칙(`F4-CM-01`~`08`)을 그대로 따른다고 가정한다. 월 이동, 날짜 클릭 시
상세 표시, 오늘 표시 등 달력 고유의 상호작용은 실제 설계 시 이 절에 채운다. **조회 전용인
Time Keeper와 달리, 캘린더는 4.2절의 자동 추가가 실현되면 쓰기 동작을 처음으로 갖게 된다** —
이는 `F4-CM-06`(F4는 F1 장부를 직접 고치지 않는다)의 예외가 생긴다는 뜻이므로 별도 검토가
필요하다.

### 4.2 F2 연동 자동 일정 추가 (미확정 — 조건부 향후 기능)

사용자가 "가능하다면"이라는 조건으로 제시한 방향이다: F2 음성 인식 결과에 "일정" 관련 내용이
있으면 자동으로 캘린더에 일정을 추가하고, 무엇이 추가됐는지 팝업으로 알린다.

**이 기능은 문서 곳곳의 기존 원칙과 바로 부딪히므로, 설계 전에 반드시 정리해야 한다.**

| 걸림돌 | 상세 |
|---|---|
| 저장할 테이블이 없다 | 3.1절이 이미 밝혔듯 일정 테이블 자체가 없다(F1-SC-01~05 미구현). 자동 추가 대상 테이블을 새로 설계해야 한다 |
| F2는 아직 일정을 만들지 않는다 | F2는 현재 매물장·구입장 필드만 채운다. 상담 발화에서 "일정"을 구조화된 데이터(날짜·종류·대상)로 뽑아내는 처리가 F2에 없다 |
| 자동 저장이 F4-CM-04·F4-CM-06과 충돌한다 | `F4-CM-04`는 "사용자가 확인·승인해야 F1 데이터가 된다", `F4-CM-06`은 "F4는 F1 장부를 직접 고치지 않는다"고 규정한다. 확인 없이 자동 저장하면 두 원칙을 모두 벗어난다 |
| 소유 모듈이 불분명하다 | 일정 데이터 저장은 원래 F1(F1-SC)이 소유하는 것으로 정리돼 있었다(6장 제외 범위 참조). 캘린더가 F4에 있어도 저장을 F1이 계속 소유할지, F4가 새로 소유할지 정해야 한다 — 이는 모듈 경계 변경이라 project-wiki 프로젝트 결정이 필요하다 |

**해소 방향 (제안, 미확정):** "자동 추가"보다 "F2가 일정 후보를 만들면 팝업이 뜨고, 사용자가
승인해야 캘린더에 실제로 얹히는" 흐름이 `F4-CM-04`에 더 맞는다. 사용자가 요청한 "어떤 사항이
일정에 추가되었다는 팝업"도 이 승인 팝업으로 겸할 수 있다. 다만 이 방향도 팀 확인 전이며 이
문서가 확정하지 않는다.

## 5. 보류 서비스 (설계 전 — 방향과 미해결 질문만 기록)

아래 네 서비스는 F4에 속하지만 **보류 상태이며 아직 설계도 구현도 하지 않았다.** 사용자가
처음 제시한 방향만 기록하며 확정된 요구사항이 아니다. 실제로 만들 때 각 서비스 문서를 이
폴더에 추가한다.

### 5.1 뉴스 요약 (보류)

날짜를 기준으로 부동산 관련 뉴스를 찾아 요약한다.

| 질문 | 왜 걸리는가 |
|---|---|
| 뉴스 출처를 무엇으로 할 것인가 | 저장소에 외부 검색·수집 연동이 없다 (`ai/`는 OpenAI SDK만, `backend/`는 런타임 HTTP 클라이언트 없음) |
| 수집 주체를 어디에 둘 것인가 | AI 모듈은 외부 I/O를 소유하지 않는다(ADR-0006). Backend adapter 또는 `data/` 파이프라인 중 선택 필요 |
| 기사 본문 저장·요약 재배포가 허용되는가 | 라이선스·저작권 확인 필요 |
| 요약에 근거를 어떻게 붙이는가 | 원문 링크·발행일을 필수로 걸지 않으면 환각 요약이 그대로 노출됨 |

### 5.2 문자 발송 초안 (보류)

만기 안내, 신규 매물 알림 등 필요한 문자의 초안을 만든다.

이미 정의된 관련 요구사항이 있어 새로 쓰기 전에 무엇을 F4로 옮길지 정해야 한다.

- F1 연락 대상 및 문자 발송 (`F1-MS-01~16`) — 초안·템플릿·치환 변수·수신 거부·최종 확인·발송 어댑터
- F3 문안 생성 (`F3-GN-01~07`) — 판단 금지, 근거 없으면 강등, 개인정보 미포함, 호출 효율
- F3 배치 판정 (`F3-BT-13~20`) — 세그먼트별 문안, 변수 치환, 일괄 승인, 실발송 경계

실발송은 계속 범위 밖이다. `F1-MS-14`의 전제(발신번호 사전등록, `(광고)` 표기, 무료 수신거부
안내, 야간 발송 금지, 수신 동의 이력)가 충족되기 전에는 어댑터를 활성화하지 않는다.

### 5.3 블로그 광고글 초안 (보류)

사용자가 제공한 글에서 어투를 파악해 광고글 초안을 만든다.

| 질문 | 왜 걸리는가 |
|---|---|
| 어투 샘플을 저장하는가 | 저장하면 보존 기간·삭제 절차 대상이 됨 (OQ-007). 세션 내 1회 사용으로 끝낼 수도 있음 |
| 매물을 특정하는 광고글인가 | 특정하면 중개대상물 표시·광고 명시의무 대상. 일반 정보성 글이면 위험 낮음 |
| 품질을 어떻게 평가하는가 | 어투 일치도는 정량 지표 설계가 어렵고 현재 MVP 평가 축과 맞지 않음 |

### 5.4 챗봇 (팀원 담당으로 이관)

F1 장부·F2 상담·F3 판단·F4 일정 화면을 오가지 않고 대화형 인터페이스로 물을 수 있게 하는
서비스. 독립 기능(F5)이 아니라 F4 안의 대화형 인터페이스로 편입한다. 챗봇 설계·구현은
팀원이 전담하기로 했으며, 1차 범위·저장·SSE 설계 정본은
[F4 챗봇 요구사항](../requirements/chatbot/overview-and-scope.md)이다. 이 문서의 초기
개인 초안(`f4-chatbot-*-draft.md`)과 로컬 프로토타입(`frontend/src/features/chatbot/`)은
위 정본으로 대체되어 제거했다.

## 8. 승인 전 처리 절차 (제안)

이 문서와 근거가 된 위키 문서(`docs/requirements/f4/*.md`)는 모두 `제안` 상태다. 팀 검토를 거쳐
승인되면 다음을 수행한다.

1. `docs/requirements/f4/overview-and-common.md`, `time-keeper.md`의 `status: 제안`을 `결정`으로
   변경한다.
2. 프로젝트 위키의 관련 open question(F4를 독립 기능으로 등록하는 안)을 닫는다.
3. 캘린더(4장)를 실제로 설계하면 `docs/requirements/f4/calendar.md`(가칭)를 새로 만들고, 이
   초안의 내용을 그대로 복사하지 않고 설계 결과로 다시 쓴다.
4. 이 초안 문서는 정본이 아니므로, 승인 후에는 삭제하거나 "승인됨" 스냅샷으로만 남긴다.
